# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

gpt-worker is a zero-API-cost dev workflow tool: ChatGPT (web subscription, via an MCP connector) acts as the planning/review "brain," while a local coding agent acts as the execution "hands." It relays messages through one fixed Cloudflare Workers hub:

```
ChatGPT Project ── MCP over HTTPS ──> Shared Hub (CF Workers) ──> Selected Workspace (Durable Object) ──> Local Bridge (WebSocket)
```

The operating protocol for *using* gpt-worker as an agent (task/wait/report loop, plan validation, timeout handling) lives in [SKILL.md](SKILL.md) and [reference/protocol.md](reference/protocol.md) — read those before driving a gpt-worker session. This file is about developing gpt-worker itself.

Zero runtime dependencies by design (see `package.json`'s `description`) — do not add npm packages to `bridge/` or `worker/src/` without a strong reason; use Node/Workers built-ins.

## Commands

```bash
npm run check    # node --check every bridge/*.mjs + worker/src/index.js (syntax only, no linter)
npm test         # node --test tests/  (built-in Node test runner)
npm run verify   # check + test — run this before considering a change done
npm run dry-run  # cd worker && wrangler deploy --dry-run
npm run deploy   # cd worker && wrangler deploy  — never run without the user's explicit go-ahead
```

Run a single test file: `node --test tests/queue.test.mjs`. Filter by name: `node --test --test-name-pattern="taskHistory" tests/`.

There is no build step and no bundler — `bridge/*.mjs` and `worker/src/index.js` run as-is (Node ESM and Cloudflare Workers ESM respectively).

## Architecture

Three independently-runnable pieces, each with a distinct execution environment:

| Piece | Where | Runs on |
|---|---|---|
| CLI / bridge | `bridge/*.mjs`, `bin/gpt-worker` | Local Node.js, as a detached background daemon |
| Relay hub | `worker/src/index.js` | Cloudflare Workers (Durable Objects), one shared deployment for every workspace |
| ChatGPT-side tools | exposed by the Worker, described in `worker/src/tools.json` | Called by ChatGPT itself, never executed locally |

### The Durable Object is the only stateful authority

`worker/src/index.js`'s `BridgeDO` class holds *everything* durable: the message queue (`msgs` table), task/protocol state (`tasks` table), per-workspace secrets (`secrets` table), and standing guidance (`settings` table) — all in its own SQLite. One workspace = one Durable Object instance (keyed by a 16-hex-char `workspace_id`, via `idFromName`), so registering a new workspace never touches another's queue, tokens, or WebSocket link. A separate hub-named DO instance (`HUB_DO_NAME = "gpt-worker-hub"`) backs the shared OAuth-protected ChatGPT connector (`/mcp`) and keeps the `workspace_registry` table (`list_workspaces`).

Local files (`bridge/state.mjs`) hold only secrets/process bookkeeping — never a second copy of task/protocol state. The machine-wide `worker.json` may also hold non-protocol `chatUrlsByWorkspace`, `conversationUrlsByWorkspace`, and `chromeTabsByWorkspace` UI mappings: a workspace URL override falls back to shared `chatUrl`; its same-Project conversation URL is the durable handoff target; its tab ID is only a process-local cache. `gpt-worker chat new` clears the latter two mappings for one workspace without changing Worker task state, while `chat attach` records a manually opened same-Project conversation and clears its stale tab cache. Once a selected tab is at a same-Project conversation URL, Chrome automation must keep its URL unchanged and insert the continuation into its composer; only a new or Project-landing tab may navigate to the URL carrying a prompt. Clear and overwrite existing composer content to maintain uninterrupted background automation. Mutate these maps through `updateWorkerConfigAtomic()` so simultaneous CLIs cannot overwrite another workspace's association. `show-config` must remain an explicit allowlist projection of browser-facing settings; never serialize raw `worker.json` or emit its Worker/authentication tokens. Chrome automation intentionally does not issue `activate` or raise the selected window: a new-window launch is best-effort background behavior, with final focus controlled by Chrome and macOS. `state.json`/`guidance.md` in the local state dir are legacy migration inputs only (see `localMigrateLegacyState` in `worker/src/index.js`); do not add new local state that duplicates what the DO already owns.

### Message flow: two queues, one Durable Object, no chat text

ChatGPT and the local agent never exchange chat text as protocol — they exchange `INIT`/`EXECUTED` (local → GPT, via `to_gpt` queue rows, delivered through the `next_task` MCP tool) and `PLAN`/`DONE`/`BLOCKED` (GPT → local, via `to_local` queue rows, delivered through `submit_plan`). Each round is tagged with a `task_id` + `iteration`; `queueSubmit` in `worker/src/index.js` rejects a reply that doesn't match the task's current `iteration`, so a stale/duplicated GPT reply can never be misapplied. The full state machine and message body formats are documented in [reference/protocol.md](reference/protocol.md) — read it before changing anything in `queueNext`/`queueSubmit`/`localStartTask`/`localReportTask`.

**Retention/purge of task bodies persisted in the DO's SQLite** (this is durable storage in the user's own Cloudflare account, unlike a pure chat/local setup — see README's Data Retention note): the `msgs` table (full INIT/EXECUTED/PLAN/DONE/BLOCKED body text) is transport-only and self-purges — `alarm()` deletes rows where `state = 'acked' AND created_at < now - RETENTION_MS` (7 days) on a 24h alarm cycle (`ALARM_INTERVAL_MS`). The `tasks` table (`goal`, `terminal_summary`, `protocol_state`) is the durable task-history source for the `queue_history` tool (`taskHistory()`) — `alarm()` purges it too, but on a longer `TASK_RETENTION_MS` (30 days, deliberately longer than `RETENTION_MS` so cross-conversation history survives week-plus gaps between sessions) and only for terminal rows (`protocol_state IN ('DONE','BLOCKED') AND updated_at < now - TASK_RETENTION_MS`) — an active (non-terminal) task is never swept regardless of age. `terminal_summary` is truncated to 500 chars only for display in `taskHistory()`'s response, not in storage. The only way to purge a *specific* task/msgs/secrets/settings/OAuth row before its retention window elapses is full workspace removal — `deprovision()`, invoked by `gpt-worker remove` — which is irreversible and does not offer a narrower "delete just this task" op.

### Local bridge: WebSocket client + 10 read-only workspace tools

`bridge/link.mjs`'s `BridgeLink` holds the outbound WebSocket to the Worker's `/link/<workspace_id>/<link_token>` endpoint (reconnects with exponential backoff, 1s → 30s). It dispatches incoming RPCs to `bridge/tools.mjs`'s `WorkspaceTools`, which implements the 10 read-only tools ChatGPT can call to inspect a workspace: `workspace_info`, `workspace_guidance`, `workspace_overview`, `list_directory`, `read_file`, `search_workspace`, `git_status`, `git_diff`, `git_log`, `execution_output`.

Three independent safety layers gate what ChatGPT can see:
- **Access window** (`link.mjs`'s `GATED_METHODS`): 8 of the 10 tools (all but `workspace_info`/`workspace_guidance`) answer `{"status":"no_active_task"}` unless a task is currently active — enforced using `__gptWorkerActiveTask`, authenticated metadata the Worker itself stamps onto every relayed call (never trust a value ChatGPT could supply). `--always-allow` on `gpt-worker start` disables this gate.
- **Sensitive-file denial** (`bridge/ignore.mjs`'s `SENSITIVE_PATTERNS`): `.env`, private keys, `.ssh/`, `.aws/`, credentials files, etc. are always blocked from reads, regardless of `.gitignore` or the access window. `NOISE_PATTERNS` are hidden from listing/search but not an error to read directly. Both pattern lists are copied verbatim from the upstream project this was inspired by (see file header) — preserve that provenance comment if you touch them.
- **Egress content sanitization** (`bridge/link.mjs`'s `reply()`, via `bridge/scanner.mjs` + `bridge/sanitize.mjs`): every reply — success or error, for every tool — is scanned for secrets by an external scanner (`betterleaks`, or `gitleaks` as a compatible fallback; see `bridge/leaks.toml`) and has every finding replaced with `[REDACTED:<RuleID>]` in place, plus local filesystem paths (workspace root, home, tmpdir, username) normalized to `[workspace]`/`[home]`/`[tmp]`/`[user]`. This is a **required external dependency**, not an optional one — `gpt-worker start` refuses to run if no working scanner is found (`bridge/cli.mjs`'s `cmdStart` calls `verifyScanner()`, which also runs a canary scan to catch a broken config or a same-named-but-wrong binary), and `reply()` fails closed: if sanitization itself throws, the original unscanned payload is never sent, an error response is sent instead. `bridge/sanitize.mjs` holds no secret-detection patterns of its own by design — see its header and the two `gw-*` rules in `bridge/leaks.toml` (which fill measured gaps in the scanner's built-in rule set; do not add a rule there that duplicates a built-in one). There is deliberately no all-or-nothing "restricted" outcome: masking always preserves line structure and never drops a whole field, unlike the upstream project this was evaluated against. Content sanitization is defense in depth, not a hard boundary — split/encoded/obfuscated secrets can still slip through a regex-based scanner; the access-window and sensitive-file layers above remain the primary controls. `betterleaks`/`gitleaks` is an external binary (Homebrew/dnf/`go install`/Docker), unrelated to the zero-npm-dependency policy above, the same way `git` itself already is.

`BridgeLink` also receives a second, unrelated push: `dashboard_task_created`, fired when a task is created through the Web dashboard rather than the CLI (see the dashboard section below). Its handler ACKs the RPC before running browser automation and swallows/logs any callback failure (via `appendLog()`), matching `plan_pushed`'s existing ack-then-side-effect shape — a failed/slow nudge must never surface as an RPC timeout back to the DO, and must never crash the daemon. The browser-automation orchestration itself (`nudgeChatGpt()` and its dependent chat-URL/tab/conversation helpers) lives in `bridge/chat-nudge.mjs`, not `bridge/cli.mjs` — extracted so both the CLI (`cmdTask`/`cmdHandoff`, stdout visible) and the daemon's `dashboard_task_created` handler (stdout discarded — a detached process — so it logs through `appendLog()` instead via `nudgeChatGpt`'s injectable `log` callback) call the identical logic. `bridge/cli.mjs` re-exports `chat-nudge.mjs`'s public names verbatim so existing imports of them from `"../bridge/cli.mjs"` (`tests/cli-parse-args.test.mjs`) keep working unchanged — don't reintroduce a second copy of these functions in `cli.mjs` itself.

### Worker routing (`worker/src/index.js`)

Path shapes at the top-level `fetch`:
- `/admin/<ADMIN_TOKEN>` — provisioning (new workspace, hub token, rotation); machine-wide, never appears in a per-workspace URL.
- `/mcp`, `/mcp/<workspace_id>` — OAuth-protected shared and per-workspace ChatGPT MCP resources. The shared resource forwards per-tool calls to the right per-workspace DO via an internal `/hub` route. `/hub` is binding-only (fetched only from `handleHubToolCall`, never routed from the top-level `fetch`), so a DO handling a `/hub` request can assume the shared connector unconditionally — `invokeTool`'s `connector` option relies on this to pick the right operating-instructions variant.
- `/link/<workspace_id>/<link_token>`, `/local/<workspace_id>/<cli_token>` — token-protected local bridge and CLI endpoints; they are not MCP connector routes.
- `/dashboard/<workspace_id>[/...]` — the workspace-owner Web dashboard (see below). Variable-length (root shell, `app.js`, `login`/`logout`, `api/*`), unlike every other route above.
- `/dashboard/hub[/...]` — the shared hub Web dashboard (see "Shared hub dashboard" below), routed to the hub DO instead of a workspace DO. `"hub"` can never collide with a real `workspace_id` (`isValidWorkspaceId` requires 16 hex chars or the legacy `"default"`), so this check runs before, and never shadows, the per-workspace one above it.

`workspace_id` is a routing key, not a secret (selects which DO instance); the actual `gpt_token`/`link_token`/`cli_token` are generated by `/admin` and validated **inside** the DO against its own `secrets` table — the top-level Worker never sees them.

### Web dashboard (`worker/src/index.js`, `BridgeDO.handleDashboard` and friends)

A browser UI for one workspace at a time, served entirely by that workspace's own DO — see `docs/plans/queue-dashboard.md` for the full design record (rejected alternatives, unresolved-at-the-time questions, and the ChatGPT review round that shaped it). It is another concrete instance of this file's "DO is the single source of truth" and "token validation stays inside the DO" invariants, not an exception to them: the top-level `fetch` only shape-validates `workspace_id` and forwards (`isValidWorkspaceId` + `idFromName`, same as `/link`/`/local`); every session/login/CSRF check happens inside `handleDashboard`.

- **Auth**: login (`handleDashboardLogin`) accepts only this workspace's own `gpt_token` via `checkResourceOwnerToken()` — never `hub_gpt_token`, because a workspace DO never has that secret set (see `checkResourceOwnerToken`'s own doc comment: hub and workspace DOs are disjoint instances). The owner token itself is never reused after login; a fresh table, `dashboard_sessions` (`session_hash` only — never the raw token, same pattern as the OAuth token tables), backs a 24h session. `createDashboardSession`/`verifyDashboardSession`/`revokeDashboardSession`/`revokeAllDashboardSessions` are the only things that touch it. `rotateSecret("gpt_token")` calls `revokeAllDashboardSessions()` (alongside the existing `revokeAllOAuthTokens()`); `deprovision()` deletes the whole table directly (it wipes every workspace table the same way, not through the individual revoke helpers); `alarm()` sweeps expired rows on its normal 24h cycle, same as OAuth codes/tokens.
- **Cookie**: `HttpOnly; Secure; SameSite=Strict; Path=/dashboard/<workspace_id>` (`dashboardSessionCookie()`). The `Path` scoping is defense in depth for a browser with multiple workspace dashboards open — the actual isolation boundary is that a session hash only ever exists in the one DO's own `dashboard_sessions` table it was created in, so a cookie sent to the wrong workspace's path always fails `verifyDashboardSession` regardless of `Path`.
- **CSRF**: every mutating (`POST`) dashboard route requires a strict same-origin `Origin` header via `checkDashboardOrigin()` — deliberately **not** the existing `checkOrigin()`, which treats a missing `Origin` as "allow" (correct for the server-to-server callers it guards, wrong here: the dashboard's session cookie is real ambient browser authority). `SameSite=Strict` alone is not treated as sufficient.
- **CSP**: `dashboardHtmlHeaders()` sets `script-src 'self'` (unlike the OAuth consent page's script-less CSP) because the dashboard needs real JS; that JS is served same-origin at `.../app.js` (`DASHBOARD_APP_JS`, `handleDashboardAppJs`), never inline.
- **Rate limiting has no bucket shared between an unauthenticated caller and an authenticated one, anywhere on this path** — `workspace_id` is not a secret, so a `/dashboard/<workspace_id>` route needs no credential to reach at all, and an earlier version of this feature gated every dashboard request (public shell, login, and the authenticated API alike) through one shared `rateLimit("dashboard", ...)` bucket before dispatch, which let an uncredentialed flood 429 an already-logged-in owner's own polling/mutations. The fix: `dashboard-public` (shell/`app.js`/logout), `dashboard-login` (POST login, tight — the credential-guessing surface), and, inside `handleDashboardApi`, whichever of `dashboard-api-unauth`/`dashboard-api` applies is chosen strictly by that same call's own `verifyDashboardSession()` outcome — never checked unconditionally up front. A request with a currently-valid session therefore only ever competes against `dashboard-api`, never against traffic hitting any of the other buckets. Preserve this when touching dashboard rate limiting: never reintroduce one bucket gating both an unauthenticated and an authenticated code path.
- **Mutation wrappers preserve existing protocol invariants, never bypass them**: `dashboardAck`/`dashboardDiscard`/`dashboardDiscardTask`/`dashboardStartTask` all call the same `local*` methods the CLI uses — never a second parallel implementation. `dashboardDiscard` specifically refuses a single-message discard of an active (non-`DONE`/`BLOCKED`) task's `to_gpt` row (`USE_DISCARD_TASK`), because `localDiscard` alone would leave `tasks.protocol_state` stuck with no queued INIT and no way for `localEnqueue`'s idempotency check to recover it — see `docs/plans/queue-dashboard.md`'s UI-constraint note for the full mechanism. `dashboardStartTask` is the one place a dashboard task is created, always through `localStartTask()` with a server-generated `task_id` and the CLI's own `"GOAL:\n<goal>"` body contract.
- **`localStartTask()` enqueue-failure consistency**: fixed as part of this feature. It now preflights the body-size check *and* a `task_id` collision check (`getTask(taskId)` — `task_id` is `tasks`' primary key, so an existing row, including the current active task under `force:true`, would otherwise either throw a raw SQL constraint error out of the `INSERT` or (`force`) BLOCK/discard the previous task before that throw) *before* any state mutation, and rolls back the freshly-inserted `tasks` row if `localEnqueue()` still fails for any other reason — previously an oversized `goal` could leave an orphaned `WAITING_PLAN` task with zero queued INIT, and with `force` could also lose the previous task. This applies to the CLI's `start_task` path too, not just the dashboard.
- **History APIs are retention-bounded, keyset-paginated, and separate from the debug/live-queue getters**: `dashboardMessages`/`dashboardTasks` are new, acked-including, full-history views — distinct from `localList()` (unacked-only, debug tool) and `taskHistory()` (terminal-only, and its `created_at` field is actually `updated_at` — a naming bug `dashboardTasks` does not repeat, using `updatedAt` correctly instead). Pagination is an opaque cursor encoding `(timestamp, tie-breaker id)` (`encodeDashboardCursor`/`decodeDashboardCursor`) — `(created_at, message_id)` for messages, `(updated_at, task_id)` for tasks — because the timestamp alone can't disambiguate same-millisecond rows. Backed by new indices (`idx_msgs_history`, `idx_msgs_task_history`, `idx_tasks_history`) distinct from the existing live-queue/active-task indices (`idx_q`, `idx_tasks_active`), which are shaped for different query patterns. "Retention-bounded" means exactly what `alarm()` already enforces elsewhere in this file — acked `msgs` past `RETENTION_MS` and terminal `tasks` past `TASK_RETENTION_MS` are simply gone, not merely hidden.
- **Browser nudge is a push, and is best-effort by design**: task creation via the dashboard is authoritative regardless of what happens next. `dashboardStartTask` calls `callLocal("dashboard_task_created", {taskId})` — a new sibling to the existing `plan_pushed` push — after the task already exists; the local daemon ACKs that RPC *before* running browser automation (`bridge/link.mjs`). `nudge.status` in `dashboardStartTask`'s response only reflects whether that RPC reached and was ACKed by the daemon (`"dispatched"`, `"local_offline"`, `"timeout"`, ...) — it says nothing about whether the Chrome automation itself (open tab, prepare composer, click send) actually succeeded, which happens *after* the ACK and is only ever observable in the local bridge log (`appendLog`), same as `plan_pushed`'s existing fire-and-forget behavior.
- **`dashboardOverview`/`dashboardMessages`/`dashboardTasks`/`dashboardSetGuidance`/`dashboardSetLimits`/`dashboardAck`/`dashboardDiscard`/`dashboardDiscardTask`/`dashboardStartTask` are dispatched through one shared method, `dashboardApiDispatch(name, method, request, url)`, extracted from `handleDashboardApi`'s former inline `if` chain.** It performs no auth itself — it must only ever be reached through an already-gated caller. There are exactly two: `handleDashboardApi` (public per-workspace route, gated by that method's own session/CSRF/rate-limit checks) and `handleHubDashboardRelay` (see below, gated instead by the *hub* DO's own checks before the call ever reaches this workspace's DO). Route a new dashboard operation through this dispatcher, not by adding a third place that calls the underlying `dashboard*`/`local*` method directly — that is what keeps hub-driven and owner-driven dashboard actions from ever disagreeing about validation/state semantics.

### Shared hub dashboard (`worker/src/index.js`, `BridgeDO.handleHubDashboard` and friends)

An owner-control-plane extension of the per-workspace dashboard above, added after the per-workspace dashboard shipped: logging in to `/dashboard/hub` with the shared `hub_gpt_token` (never a workspace's own `gpt_token` — same disjoint-secret guarantee `checkResourceOwnerToken`'s doc comment relies on) gives one browser session that can view and operate on every workspace in the hub DO's own `registeredWorkspaces()` (the `workspace_registry` table), not just one.

- **Reframing "Workspace isolation between DOs" for this feature, explicitly**: this is not an exception to that invariant, it is the owner's own control plane across workspaces *they already registered here themselves* — never a new way for one workspace to reach another, and never a way for anyone without the hub token to reach any workspace. Concretely: a hub session cannot authenticate a workspace's own `/dashboard/<id>/api/*` (different DO, different `dashboard_sessions` table, different cookie `Path`); a workspace session cannot authenticate the hub's `/dashboard/hub/api/*`; and the hub can only ever reach a `workspace_id` present in its own `registeredWorkspaces()` — never an arbitrary valid-looking 16-hex id, even though `isValidWorkspaceId` alone would accept it. Preserve this membership check (`hubDashboardRelay`, mirroring the existing `handleHubToolCall`'s identical check for the MCP tool relay) if you touch hub dashboard routing.
- **Authorization propagation, hub DO → workspace DO: a binding-only internal relay, not a forwarded token.** `hubDashboardRelay`/`hubDashboardWorkspaces` (hub DO) call a new internal-only route, `POST /hub-dashboard-relay` (`handleHubDashboardRelay`, workspace DO) — reachable only via a `BRIDGE_DO` binding call, never routed from a public URL (no path shape in the top-level `fetch` maps to it), exactly the same shape as the pre-existing `/hub` route (`handleHubRelay`) used for the MCP tool relay. The hub DO has already verified its own dashboard session, CSRF origin, rate limit, and registry membership *before* this is ever called; the workspace DO does not (and structurally cannot) re-derive who the hub-side browser caller was — the binding call itself is the authority, same as `/hub`. **The hub's session cookie and `hub_gpt_token` are never forwarded to the workspace DO** — only the already-authorized operation name/method/query/body. This is what keeps "token validation stays inside the DO" true for this feature too: `hub_gpt_token` is validated only inside the hub DO, never copied to or re-checked by a workspace DO. Do not "simplify" this by forwarding the hub token to the workspace DO and letting it validate there — `checkResourceOwnerToken()`'s `hub_gpt_token || gpt_token` OR-check exists for OAuth's single-DO-is-either-role case, not as a cross-DO trust mechanism, and reusing it that way would let a hub token authenticate a request that looks like it came from the workspace's own owner.
- **A registry entry can outlive a workspace's own `deprovision()`** — `unregister_workspace` and `deprovision` are two separate `/admin` calls (see `bridge/cli.mjs`'s `cmdRemove`, which issues both), so a stale registered-but-deprovisioned target is expected, not a bug to "fix" by making them atomic. `handleHubDashboardRelay` guards this with its own `hasSecrets()` check (`NOT_PROVISIONED`) rather than silently recreating task/settings state for a workspace that no longer has tokens; `hubDashboardWorkspaces` surfaces that per-entry as `{overview: null, error: "NOT_PROVISIONED"}` rather than failing the whole listing.
- **Session/cookie**: reuses the exact same `dashboard_sessions` table, `createDashboardSession`/`verifyDashboardSession`/`revokeDashboardSession`/`revokeAllDashboardSessions` methods, and `dashboardSessionCookie()` helper as the per-workspace dashboard — just called on the hub DO's own instance of that table, and with the literal string `"hub"` in place of a `workspace_id`, which naturally produces `Path=/dashboard/hub`. No new session mechanism was introduced. `rotateHubToken()` now also calls `revokeAllDashboardSessions()` (mirroring `rotateSecret("gpt_token")`'s existing call for the per-workspace case), so rotating the shared hub token immediately cuts off hub dashboard sessions issued under the old value; it does not touch any workspace DO's own sessions, and rotating a workspace's `gpt_token` does not touch the hub's.
- **Rate limiting uses its own bucket names, never shared with a workspace's own dashboard buckets**: `hub-dashboard-public`, `hub-dashboard-login`, `hub-dashboard-api-unauth`, `hub-dashboard-api` (hub DO, same two-tier unauthenticated/authenticated split as the per-workspace `dashboard-*` buckets, and the same reasoning: an unauthenticated flood must never 429 an already-authenticated caller), plus `hub-dashboard-internal` (workspace DO, consumed only by `handleHubDashboardRelay` — so a burst of hub-driven management traffic into one workspace can never rate-limit that workspace's own owner dashboard, or vice versa).
- **Envelope size gate uses the same fixed-ceiling pattern as `handleOAuthMcpDispatch`'s hub-level branch, for the identical reason**: `hubDashboardRelay` doesn't know the target workspace's own `max_body_bytes` setting before relaying (that's per-workspace DO state), so its own pre-relay size check uses `MAX_REQUEST_BYTES_CEILING` rather than a precise value; the real, precise limit is enforced once the call reaches the target's own `dashboardApiDispatch` via `this.maxRequestBytes()`. Do not "fix" this asymmetry by widening it — see that existing comment for why it's deliberate.
- **UI**: `renderHubDashboardLoginHtml`/`renderHubDashboardShellHtml`/`HUB_DASHBOARD_APP_JS` are a structurally-parallel but separate set from the per-workspace `renderDashboardLoginHtml`/`renderDashboardShellHtml`/`DASHBOARD_APP_JS` (same look, CSP, and textContent-only rendering discipline — see the latter's own doc comment for why untrusted content is never inlined as HTML), extended with a workspace list/selector step. Every per-workspace action in the hub UI targets `/dashboard/hub/api/workspaces/<id>/...` instead of `/dashboard/<id>/api/...`.

### CLI (`bridge/cli.mjs`)

`gpt-worker handoff` and `gpt-worker report` (`cmdHandoff`/`cmdReport`) are the same round — both delegate to `reportRound(args, handoff)`; the only difference is the `HANDOFF:` section `buildExecutedBody()` appends and the closing message. `handoff` deliberately covers *both* directions of a hand-off — the agent that did this round's work stopping, or a fresh agent proactively taking over a round the previous agent left without reporting — with a single command and a plain-language `reason`, not a mode/trigger flag: `report_task` doesn't know or care which local agent is calling it, only `task_id`/`iteration`/protocol state, so nothing server-side distinguishes the two callers anyway. When claiming an abandoned round, pass an honest `reason` and skip `--changed`/`--tests` (or say plainly nothing is verified) rather than inventing a report — the `"?"`/`"(not run)"` defaults already exist for exactly this, and `EXECUTED` review (`worker/src/instructions.md` §7) already requires GPT to re-verify via `git_status`/`git_diff` regardless of who's asking, so no extra field is needed to make GPT skeptical. `report_task`'s ordinary `EXECUTING`-only precondition is what makes a claiming `handoff` valid in exactly the situation it's for (a round left mid-execution) and invalid otherwise (`INVALID_STATE` when a reply is already queued — `wait` picks that up, not another `handoff`). Do not reintroduce a `claim` subcommand or a `trigger` field for this — it was tried and reverted; the free-text `reason` plus the existing state precondition already cover it, and CHANGED_FILES/TESTS' own long-standing `"?"`/empty defaults already say "unspecified." Agent-to-agent handoff needs no per-agent state precisely *because* of the invariants below: `localPoll` selects `to_local` rows without looking at who asked, `selectWaitMessages` filters by `task_id` alone, and `cmdWait` reads the active task from the DO rather than from local state — so a second agent resumes with a plain `wait`. Do not add an agent identity or a queue-level lease/lock to "fix" this; sequential handoff does not race, and that filtering is what makes the feature work. The receiving side keys off a `HANDOFF_BRIEF:` marker at the start of a PLAN body (written by ChatGPT per `worker/src/instructions.md` §8), so treat that marker as protocol, not cosmetics.

`gpt-worker limits` reads/writes a workspace's own `settings.max_body_bytes` (`BridgeDO#maxBodyBytes()`/`localMaxBodyBytesGet()`/`localMaxBodyBytesSet()`), overriding the `MAX_BODY_BYTES` (16 KiB) default up to `MAX_BODY_BYTES_CEILING` (256 KiB). It is per-workspace DO state, not a Worker-wide constant — no redeploy needed to change it, consistent with the DO-is-the-authority invariant elsewhere in this file. `maxRequestBytes()` (`maxBodyBytes() + REQUEST_ENVELOPE_OVERHEAD_BYTES`) must stay in sync wherever `body` is size-checked: `queueSubmit`/`localEnqueue` check the body itself, `handleLocalRoute`/`handleHubRelay`/the dedicated-connector branch of `handleOAuthMcpDispatch` check the request envelope around it. The shared connector's hub-level envelope gate (`handleOAuthMcpDispatch`'s `useHubHandler` branch) is the one exception — it runs on the hub DO before `arguments.workspace_id` has been parsed out, so it can't yet know which workspace's limit applies and is fixed at `MAX_REQUEST_BYTES_CEILING` instead; the real per-workspace limit is enforced once `handleHubToolCall` forwards the call to that workspace's own DO (`handleHubRelay`). Do not widen this gate's fixed ceiling to "fix" that asymmetry — it is deliberate, not a gap.

Each `gpt-worker <cmd>` subcommand talks to the Worker over `/local/<workspace_id>/<cli_token>` (`localCall`) for queue/task operations. `cmdWait` (the most failure-prone command to modify) already polls the Worker in ~20s chunks for its whole `--timeout` window (default 900s) — it is a single blocking call by design; if you change its retry/backoff behavior, keep that property, since [SKILL.md](SKILL.md) explicitly instructs agents to call it once and let it block rather than wrapping it in their own sleep/retry loop.

## Key invariants to preserve when editing

- **DO is the single source of truth for task/protocol state.** Never let the CLI or bridge reconstruct or cache task state independently (see the comment at the top of `bridge/state.mjs`).
- **Workspace isolation between DOs.** A change to routing or `idFromName` calls must not let one workspace's queue, tokens, or WebSocket link become reachable from another's.
- **Token validation stays inside the DO**, not at the top-level Worker `fetch`.
- **Exactly two trusted inputs, with different provenance.** (1) The Worker-owned operating protocol in `worker/src/instructions.md`, parsed by `worker/src/instructions.js` — static text compiled into the Worker, delivered in `InitializeResult.instructions`, by the `operating_instructions` tool, and in the `operating_instructions` field of a non-empty `next_task` result. It is trusted because nothing outside this repository can reach it; never interpolate workspace, CLI, or ChatGPT data into it. (2) `workspace_guidance` — the only trusted input from the **local** side, set through the owner-authenticated CLI. Everything else ChatGPT reads is untrusted workspace data (see `UNTRUSTED_NOTE` in `bridge/tools.mjs` and the protocol doc). Don't blur either line when adding new tools.
- **Local state files are private by default** (`0700` dirs / `0600` files, self-healed by `fixPermissions()` in `bridge/state.mjs`) — any new local state file must go through the same helpers, not raw `fs.writeFileSync`.
- **Idempotent enqueue**: `localEnqueue` reuses an existing message for a repeated `(task_id, iteration)` instead of creating a duplicate, since a CLI retry after a dropped HTTP response must not double-post. Preserve this if you touch queueing.

## Tests

`tests/` uses Node's built-in test runner (`node --test`) against a fake Durable Object context (`tests/helpers/fake-do-ctx.mjs`) or a real temporary git repo (`tests/tools-containment.test.mjs`), not Miniflare — `queue.test.mjs` and `admin.test.mjs` import the real `BridgeDO` methods from `worker/src/index.js` and exercise them directly against `this.sql`, so DO logic changes are covered without deploying. When adding a workspace tool or a queue/admin op, add or extend a test in the matching file rather than introducing a new test harness. `tests/dashboard.test.mjs` follows `tests/oauth.test.mjs`'s pattern instead (a real `BridgeDO` instance behind the same `env.BRIDGE_DO` binding shape, routed through the actual top-level `worker.fetch`) because dashboard routing/session/CSRF/workspace-isolation behavior lives partly in the top-level `fetch`, which a `makeFakeCtx()`-only DO instantiation doesn't exercise. `tests/link.test.mjs` covers `BridgeLink`'s RPC dispatch (currently just `dashboard_task_created`'s ack-before-callback ordering and failure isolation) against a fake in-memory WebSocket, not a real connection.
