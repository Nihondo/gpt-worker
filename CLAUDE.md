# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

gpt-worker is a zero-API-cost dev workflow tool: ChatGPT (web subscription, via an MCP connector) acts as the planning/review "brain," while a local coding agent acts as the execution "hands." It relays messages through one fixed Cloudflare Workers hub:

```
ChatGPT Project ── MCP over HTTPS ──> Shared Hub (CF Workers) ──> Selected Workspace (Durable Object) ──> Local Bridge (WebSocket)
```

The operating protocol for *using* gpt-worker as an agent (task/wait/report loop, plan validation, timeout handling) lives in [SKILL.md](SKILL.md) and [reference/protocol.md](reference/protocol.md) — read those before driving a gpt-worker session. This file is about developing gpt-worker itself.

Zero runtime dependencies by design (see `package.json`'s `description`) — do not add npm packages to `bridge/` or `worker/src/` without a strong reason; use Node/Workers built-ins.

## Commands

```bash
npm run check    # node --check every bridge/*.mjs, every worker/src/*.js and worker/src/dashboard/*.js (dynamically enumerated by scripts/check.mjs; syntax only, no linter)
npm test         # node --test --import ./tests/helpers/text-modules.mjs tests/  (built-in Node test runner; the --import shim is what lets Node load the dashboard Text modules)
npm run coverage # same test suite with Node's experimental coverage report; intentionally not part of verify
npm run verify   # check + test — run this before considering a change done
npm run dry-run  # cd worker && wrangler deploy --dry-run
npm run deploy   # cd worker && wrangler deploy  — never run without the user's explicit go-ahead
```

Run a single test file: `node --test --import ./tests/helpers/text-modules.mjs tests/queue.test.mjs`. Filter by name: add `--test-name-pattern="taskHistory"`. **The `--import` shim is not optional** — without it any test that reaches `worker/src/index.js` dies with `ERR_UNKNOWN_FILE_EXTENSION` on `instructions.md`, because Wrangler Text modules are not something Node can load on its own.

There is no build step and no bundler — `bridge/*.mjs` and `worker/src/*.js` run as-is (Node ESM and Cloudflare Workers ESM respectively).

## Architecture

Three independently-runnable pieces, each with a distinct execution environment:

| Piece | Where | Runs on |
|---|---|---|
| CLI / bridge | `bridge/*.mjs`, `bin/gpt-worker` | Local Node.js, as a detached background daemon |
| Relay hub | `worker/src/index.js` (composition root) + `worker/src/bridge-*.js` / `worker-*.js` (see "Worker module layout") | Cloudflare Workers (Durable Objects), one shared deployment for every workspace |
| ChatGPT-side tools | exposed by the Worker, described in `worker/src/tools.json` | Called by ChatGPT itself, never executed locally |

### The Durable Object is the only stateful authority

`worker/src/index.js`'s `BridgeDO` class (its logic split across the domain modules under "Worker module layout") holds *everything* durable: the message queue (`msgs` table), task/protocol state (`tasks` table), per-workspace secrets (`secrets` table), and standing guidance (`settings` table) — all in its own SQLite. One workspace = one Durable Object instance (keyed by a 16-hex-char `workspace_id`, via `idFromName`), so registering a new workspace never touches another's queue, tokens, or WebSocket link. A separate hub-named DO instance (`HUB_DO_NAME = "gpt-worker-hub"`) backs the shared OAuth-protected ChatGPT connector (`/mcp`) and keeps the `workspace_registry` table (`list_workspaces`).

Local files (`bridge/state.mjs`) hold only secrets/process bookkeeping — never a second copy of task/protocol state. The machine-wide `worker.json` may also hold non-protocol `chatUrlsByWorkspace`, `conversationUrlsByWorkspace`, and `chromeTabsByWorkspace` UI mappings: a workspace URL override falls back to shared `chatUrl`; its same-Project conversation URL is the durable handoff target; its tab ID is only a process-local cache. `gpt-worker chat new` clears the latter two mappings for one workspace without changing Worker task state, while `chat attach` records a manually opened same-Project conversation and clears its stale tab cache. Once a selected tab is at a same-Project conversation URL, Chrome automation must keep its URL unchanged and insert the continuation into its composer; only a new or Project-landing tab may navigate to the URL carrying a prompt. Clear and overwrite existing composer content to maintain uninterrupted background automation. Mutate these maps through `updateWorkerConfigAtomic()` so simultaneous CLIs cannot overwrite another workspace's association. `show-config` must remain an explicit allowlist projection of browser-facing settings; never serialize raw `worker.json` or emit its Worker/authentication tokens. Chrome automation intentionally does not issue `activate` or raise the selected window: a new-window launch is best-effort background behavior, with final focus controlled by Chrome and macOS. `state.json`/`guidance.md` in the local state dir are legacy migration inputs only (see `localMigrateLegacyState` in `worker/src/bridge-protocol.js`); do not add new local state that duplicates what the DO already owns.

### Message flow: two queues, one Durable Object, no chat text

ChatGPT and the local agent never exchange chat text as protocol — they exchange `INIT`/`EXECUTED` (local → GPT, via `to_gpt` queue rows, delivered through the `next_task` MCP tool) and `PLAN`/`DONE`/`BLOCKED` (GPT → local, via `to_local` queue rows, delivered through `submit_plan`). Each round is tagged with a `task_id` + `iteration`; `queueSubmit` in `worker/src/bridge-protocol.js` rejects a reply that doesn't match the task's current `iteration`, so a stale/duplicated GPT reply can never be misapplied. The full state machine and message body formats are documented in [reference/protocol.md](reference/protocol.md) — read it before changing anything in `queueNext`/`queueSubmit`/`localStartTask`/`localReportTask`.

**Retention/purge of task bodies persisted in the DO's SQLite** (this is durable storage in the user's own Cloudflare account, unlike a pure chat/local setup — see README's Data Retention note): the `msgs` table (full INIT/EXECUTED/PLAN/DONE/BLOCKED body text) is transport-only and self-purges — `alarm()` deletes rows where `state = 'acked' AND created_at < now - RETENTION_MS` (7 days) on a 24h alarm cycle (`ALARM_INTERVAL_MS`). The `tasks` table (`goal`, `terminal_summary`, `protocol_state`) is the durable task-history source for the `queue_history` tool (`taskHistory()`) — `alarm()` purges it too, but on a longer `TASK_RETENTION_MS` (30 days, deliberately longer than `RETENTION_MS` so cross-conversation history survives week-plus gaps between sessions) and only for terminal rows (`protocol_state IN ('DONE','BLOCKED') AND updated_at < now - TASK_RETENTION_MS`) — an active (non-terminal) task is never swept regardless of age. `terminal_summary` is truncated to 500 chars only for display in `taskHistory()`'s response, not in storage. The only way to purge a *specific* task/msgs/secrets/settings/OAuth row before its retention window elapses is full workspace removal — `deprovision()`, invoked by `gpt-worker remove` — which is irreversible and does not offer a narrower "delete just this task" op.

### Local bridge: WebSocket client + 10 primitive workspace tools + workspace_batch + workspace_bundle

`bridge/link.mjs`'s `BridgeLink` holds the outbound WebSocket to the Worker's `/link/<workspace_id>/<link_token>` endpoint (reconnects with exponential backoff, 1s → 30s). It dispatches incoming RPCs to `bridge/tools.mjs`'s `WorkspaceTools`, which implements the 10 primitive read-only tools ChatGPT can call to inspect a workspace: `workspace_info`, `workspace_guidance`, `workspace_overview`, `list_directory`, `read_file`, `search_workspace`, `git_status`, `git_diff`, `git_log`, `execution_output`, alongside the batch execution wrapper `workspace_batch` and the archive tool `workspace_bundle` (12 tools total; see "workspace_bundle" below).

Three independent safety layers gate what ChatGPT can see:
- **Access window** (`link.mjs`'s `GATED_METHODS`): 10 of the 12 tools (all but `workspace_info`/`workspace_guidance`) answer `{"status":"no_active_task"}` (no non-terminal task exists) or `{"status":"task_window_expired"}` (one exists but has been idle past `TASK_WINDOW_IDLE_MS`, 1h) unless a task's read window is open — enforced using `__gptWorkerActiveTask` plus `__gptWorkerTaskWindow`, authenticated metadata the Worker itself stamps onto every relayed call (never trust a value ChatGPT could supply). `taskWindowState()` in `bridge-mcp.js` owns the three-valued state (`"none"`/`"expired"`/`"active"`) and `isActiveTaskWindow()` is its boolean wrapper; `taskWindowInfo()` exposes the ceiling and expiry so the CLI never copies the constant. **The window is anchored on `tasks.updated_at` — the last protocol transition — not on `tasks.task_started_at`**, which is display-only (`taskView` → the dashboard's "started <time>") and must never be UPDATEd: anchoring on the start time silently revoked every gated read one hour into a task that was still progressing, and ChatGPT could not tell that from "no task exists". ChatGPT cannot extend the window at will — `queueSubmit` requires a not-yet-acked `to_gpt` row for the current iteration and then moves the task to `WAITING_LOCAL`, so at most one transition per round comes from the GPT side and the next one needs a cliToken-authenticated local ack. `__gptWorkerActiveTask` **must stay a boolean**: `link.mjs` reads it with `!!(...)`, so sending the string `"expired"` in it would make an older bridge treat a closed window as truthy and fail open — that is exactly why the three-valued state travels in its own key, which an older bridge ignores while still refusing correctly. `--always-allow` on `gpt-worker start` disables this gate.
- **Sensitive-file denial** (`bridge/ignore.mjs`'s `SENSITIVE_PATTERNS`): `.env`, private keys, `.ssh/`, `.aws/`, credentials files, etc. are always blocked from reads, regardless of `.gitignore` or the access window. `NOISE_PATTERNS` are hidden from listing/search but not an error to read directly. Both pattern lists are copied verbatim from the upstream project this was inspired by (see file header) — preserve that provenance comment if you touch them.
- **Egress content sanitization** (`bridge/link.mjs`'s `reply()`, via `bridge/scanner.mjs` + `bridge/sanitize.mjs`): every reply — success or error, for every tool — is scanned for secrets by an external scanner (`betterleaks`, or `gitleaks` as a compatible fallback; see `bridge/leaks.toml`) and has every finding replaced with `[REDACTED:<RuleID>]` in place, plus local filesystem paths (workspace root, home, tmpdir, username) normalized to `[workspace]`/`[home]`/`[tmp]`/`[user]`. This is a **required external dependency**, not an optional one — `gpt-worker start` refuses to run if no working scanner is found (`bridge/cli-daemon.mjs`'s `cmdStart` calls `verifyScanner()`, which also runs a canary scan to catch a broken config or a same-named-but-wrong binary), and `reply()` fails closed: if sanitization itself throws, the original unscanned payload is never sent, an error response is sent instead. `bridge/sanitize.mjs` holds no secret-detection patterns of its own by design — see its header and the two `gw-*` rules in `bridge/leaks.toml` (which fill measured gaps in the scanner's built-in rule set; do not add a rule there that duplicates a built-in one). There is deliberately no all-or-nothing "restricted" outcome: masking always preserves line structure and never drops a whole field, unlike the upstream project this was evaluated against. Content sanitization is defense in depth, not a hard boundary — split/encoded/obfuscated secrets can still slip through a regex-based scanner; the access-window and sensitive-file layers above remain the primary controls. `betterleaks`/`gitleaks` is an external binary (Homebrew/dnf/`go install`/Docker), unrelated to the zero-npm-dependency policy above, the same way `git` itself already is. **The scanned text is untrusted workspace content, so nothing in it may switch detection off** — both were measured, not assumed: (1) by default a `gitleaks:allow` / `betterleaks:allow` comment on a line suppresses the finding on it, so every scan passes `--ignore-gitleaks-allow`; (2) the scanner reads `.gitleaksignore` from its working directory and a `stdin` finding's fingerprint is the predictable `:<rule>:<line>`, while `--gitleaks-ignore-path` is *not* honored by `stdin`, so `scanText()` runs the scanner from an empty private directory (`scannerCwd()`) rather than the daemon's inherited cwd (normally the workspace). `scanDirectory()` (see below) points the ignore lookup at an empty directory instead. `tests/scanner.test.mjs` pins both, and was verified to fail without the fix.

**Every synchronous child process on the tool-call and browser-automation paths has a time budget** (`bridge/exec-limits.mjs`); the exceptions are deliberate and listed below (`ps`, `runWrangler`, and the secret scanner, which carries its own `SCAN_TIMEOUT_MS`). The bridge daemon is one Node process and each `execFileSync` blocks its whole event loop, so a hung `git` or `osascript` used to freeze every RPC the daemon serves while the Worker gave up after its own 20s `RPC_TIMEOUT_MS`. Tool calls (`git`/`rg`) get 15s — deliberately shorter than the Worker's 20s so the bridge answers with a structured error first — the per-path gitignore probes get 5s, the OS URL opener 10s, and `osascript` gets `25s + 2 x enterDelayMs` (`osascriptTimeoutMs`, so a raised `enterDelayMs` is never timed out by its own setting; SIGKILL, because osascript stuck on an Apple Event ignores SIGTERM). A timeout must never be mistaken for an answer: `search_workspace` returns `SEARCH_TIMEOUT` instead of the *partial* stdout it used to fall through to (which would present an incomplete search as complete), `git_status`/`git_diff`/`git_log` return `GIT_TIMEOUT` instead of `{isRepo:false}`/`GIT_ERROR`, and — the case that matters most — **`IgnoreRules.isGitIgnored` fails CLOSED on anything but a definite answer**. Only `git check-ignore` exiting 1 means "not ignored"; a timeout, exit 128 (git could not decide: a broken `.git`, dubious ownership, a path beyond a symlink) and a git that cannot be run at all all deny. The `rev-parse` probe means "this is a plain directory" only when git says "not a git repository" (run with `LC_ALL=C` so the wording is stable across locales); every other failure of it — a timeout, a missing git, a repository git refuses to open — denies and leaves `isGitRepository` unset, because concluding "not a repository" would switch the whole check off for every path. (Exit 128 used to read as "not ignored", which exposed gitignored files exactly when git was misbehaving.) A `.git` entry (a directory, or the pointer file a worktree/submodule uses) anywhere from the workspace up to the filesystem root contradicts "not a git repository": git reports a **damaged** repository (verified with a real git and a missing `.git/HEAD`) with exactly the words it uses for a plain directory, so the message alone cannot tell them apart, and treating it as "plain" made every gitignored file readable. When git denies because it could not answer, the `ACCESS_DENIED_GITIGNORED_FILE` response carries a `message` saying so (`IgnoreRules.unknownReason`), so the operator is not left hunting for a `.gitignore` rule that does not exist. What git has told us is scoped to an **operation** — one tool call — not cached for the life of the daemon or approximated with timers (which is what this replaced, and each timer left a different hole). `WorkspaceTools` wraps the tools that consult the gitignore check (`OPERATION_METHODS`) in `runOperation`; only the outermost call opens and closes the operation, so a tool that calls another (`workspaceOverview` → `readFile`) stays in one. At the start of each operation git is asked afresh whether the directory is a repository, so a `git init` after the daemon started (reproduced: `.gitignore` used to stay unenforced until restart), a repository going away (used to leave every path denied until restart), or a `GIT_DIR`/`GIT_WORK_TREE` layout with no `.git` in the workspace are all seen by the very next tool call, with no window. Inside the operation that verdict is held, and anything git could not answer is **shared**: a 500-entry listing against a git that fails fast asks once, not 500 times (an odd single path is different — per-path `check-ignore` failures only count as "git is broken" after 3 in a row, and any definite answer resets the streak). A git *timeout* is remembered even across operations, for 10s, because each ask costs a whole timeout. A call made outside any operation is its own operation. The number of paths denied *because git could not answer* is counted, and a result that looks empty for that reason carries `partial: true`, `hiddenByGitCheck: N` and a `warning` (errors are left alone: they already say what went wrong) — so "nothing here" and "git could not vouch for anything here" are different answers, in keeping with "a timeout is never an answer". `hasGitMarker` honors `GIT_CEILING_DIRECTORIES` as git does, and treats any lstat error other than ENOENT/ENOTDIR as "a marker may exist" (it is an access control: "I could not look" must not read as "there is none"); git's other boundary, a change of filesystem, is not reproduced (that error lands on the deny side: availability, not safety). The availability cost of the whole design is real and deliberate: a workspace on a machine with no working `git` cannot be confirmed to be a plain directory, so reads are denied — git is a prerequisite. Do not "simplify" any of this into `false`. `workspace_info` reports `git.isRepo: null` with `error: "GIT_TIMEOUT"` when git does not answer, rather than the false claim that the directory is not a repository, and `search_workspace` no longer reads every non-zero exit as "no matches": exit 1 is the only "no matches"; a failure with no output is `SEARCH_FAILED` (a malformed regex used to look like "nothing found"), and hits printed before an abnormal exit are kept but returned with `partial: true` and a `warning` (rg exits 2 when it printed matches but could not read some paths, which is ordinary, so dropping them would be a regression and presenting them as complete would be a lie). The one-time `rg --version` probe is time-limited too (an `rg` that does not answer counts as unavailable, so search falls back to `git grep`). (`ps` in `state.mjs` deliberately has **no** timeout: a timeout would be indistinguishable from "process not found", making `checkPid` report a live daemon as dead and letting `cmdStart` launch a second one.) `GPT_WORKER_EXEC_TIMEOUT_MS` overrides every budget above, and exists only for tests.

### workspace_bundle: a scanned, masked `.tgz` delivered as an MCP embedded resource

`WorkspaceTools.workspaceBundle()` (`bridge/tools.mjs`) packs every text file ChatGPT may currently read into one archive, so a broad read is one call instead of one `read_file` per file. Design record, including the measured Phase 0/1 results: `docs/plans/pending/workspace-bundle-tool.md` (gitignored). The ordinary tools return text in the tool result; this one returns a file.

- **The read policy is reused, never reimplemented.** Directories are pruned with `isBrowseHidden()` (the rule `listDirectory`/search use); each file must pass `readPolicy(rel, { directRead: false })`, so a Git-ignored path the owner `allow-read`ed stays direct-read-only and is *not* bundled (verified against a real `docs/` allow-read). Hidden paths are omitted **without a name or a count** — in the archive, in `BUNDLE.md` and in the tool result; only entries `list_directory` already shows (binary, symlink, oversize, withheld) are named. The start directory needs the directory form of the sensitive check (`isSensitive(rel, true)`), because `readPolicy()` judges files (`.ssh/` is a directory-only pattern); the answer is identical whether or not the directory exists. Symlinks are never followed; files are opened `O_NOFOLLOW`; text that is not valid UTF-8 is treated as binary because masking would corrupt it. The whole call runs in one `runOperation()` (it is in `OPERATION_METHODS`), so git failing is reported as `partial`/`hiddenByGitCheck`/`warning` — "git could not vouch for anything" is never presented as an empty workspace.
- **Pipeline:** collect (path order, time budget) -> stage a copy under the state dir (`bundleStagingDir()`, 0700; stale `run-*` dirs are swept) -> **one** `scanDirectory()` run over the copy -> mask (`applyFindings()`, then `redactLocalPaths()`) -> write `BUNDLE.md` (itself passed through `sanitizeText()`) -> `tar --no-xattrs -czf` with `COPYFILE_DISABLE=1` (macOS bsdtar otherwise adds extended attributes twice over, both measured: `._*` AppleDouble entries, and PAX headers such as `LIBARCHIVE.xattr.com.apple.provenance` — they can carry things like a download URL, and readers warn about them; a tar that rejects `--no-xattrs` is retried without it) -> base64. **It fails closed:** a scan that fails, times out or returns a report that cannot be trusted (a path outside the scanned directory, or a file that was never staged) produces `BUNDLE_SCAN_FAILED` and no archive; a finding whose secret is not present verbatim in its file (found by decoding) cannot be masked in place, so **that file is withheld** and listed in `BUNDLE.md`. A directory scan with nothing to report writes a literal JSON `null`, not `[]` — `scanDirectory()` accepts exactly that and nothing else that is not a list.
- **A second egress path, with one narrow exception to "`reply()` is the single egress point".** A base64 archive has no meaningful string leaves — scanning it would spend the 2s scan budget and find nothing — so the bridge returns it wrapped in `PreScanned` (`bridge/sanitize.mjs`), and `reply()` skips exactly that class (`collectStringLeaves`/`rebuildWithLeaves` pass it through; `expandPreScanned()` turns it into the wire form and adds its masking counts to the `sanitize` summary). The exception is safe because of *what is skipped*: content that was already scanned as files, per file with paths, **before** it was packed. Everything ChatGPT can supply reaches the bridge as plain JSON, which can never be a `PreScanned`, and a plain object shaped like the wire form is scanned like any other text (tested). Never construct a `PreScanned` from anything but a finished scan-and-mask pipeline; never widen `reply()` to skip by shape or by field name.
- **Delivery.** The Worker (`worker/src/bridge-mcp.js`) turns the wire form into `content: [text, {type:"resource", resource:{uri, mimeType, blob}}]` via `toolBlob()`, validating base64/mime/filename, and keeps the blob **out of `structuredContent`** — `toolOk()` duplicates its data into both, which would double the payload. Do not route a blob through `toolOk()`. Only `workspace_bundle` gets this treatment.
- **Limits and budgets.** Archive default 1 MiB, max 4 MiB (the largest size measured to reach ChatGPT intact); over `max_bytes` is `BUNDLE_TOO_LARGE` with a per-path breakdown of visible paths and **no partial archive**; per file 1 MiB, raw text 16 MiB. It runs synchronously on the daemon's one thread, so its three stages have budgets summing below the Worker's 20s `RPC_TIMEOUT_MS` (collect 8s, scan 6s, `tar` 5s; `bridge/exec-limits.mjs`): the time budget stops the walk and flags the archive `partial` rather than failing. Every RPC the daemon serves waits meanwhile.
- **ChatGPT has its own approval step, which gpt-worker cannot see or control.** Before materializing the attachment ChatGPT asks the user ("ファイルを実体化しますか？" — Deny / Allow, with "Allow for this conversation" under the arrow). Measured: declining replaces the *whole* tool result with a platform error ("...ユーザーは拒否しました。このパスの呼び出しは今後行わないでください") — the text part with `BUNDLE.md`'s counts is not seen, which is why warnings are also written into `BUNDLE.md` — and ChatGPT stops rather than falling back on its own, so the tool description carries the fallback instruction; an unanswered dialog was still pending after 15 minutes, so an unattended run can stall indefinitely and `wait` cannot tell why. From the bridge and Worker this is a successful call, so the MCP Access tab records `success` for a declined or unanswered one.
- **ChatGPT caches a connector's tool list.** After changing `tools.json` (arguments, description), the connector must be refreshed in ChatGPT's settings: until then ChatGPT validates calls against the *old* schema (measured: `path` was rejected as an unexpected property after deploy) and reads the old description.

`BridgeLink` also receives a second, unrelated push: `dashboard_task_created`, fired when a task is created through the Web dashboard rather than the CLI (see the dashboard section below). Its handler ACKs the RPC before running browser automation and swallows/logs any callback failure (via `appendLog()`), matching `plan_pushed`'s existing ack-then-side-effect shape — a failed/slow nudge must never surface as an RPC timeout back to the DO, and must never crash the daemon. The browser-automation orchestration itself (`nudgeChatGpt()` and its dependent chat-URL/tab/conversation helpers) lives in `bridge/chat-nudge.mjs`; `bridge/cli-task.mjs` calls it for CLI task/report rounds (stdout visible), while `bridge/cli-daemon.mjs` calls it for `dashboard_task_created` (stdout discarded, so its injectable `log` callback routes through `appendLog()`). `bridge/cli.mjs` is the compatibility facade and explicitly re-exports `chat-nudge.mjs`'s public names so existing imports of them from `"../bridge/cli.mjs"` (`tests/cli-parse-args.test.mjs`) keep working unchanged — don't reintroduce a second copy of these functions in `cli.mjs` itself.

### Worker module layout (`worker/src/`)

`worker/src/index.js` is the **composition root**: the default `fetch` export, top-level routing and the `/admin`/OAuth public route handlers, `alarm()`, cross-cutting constants (`HUB_DO_NAME`, `RETENTION_MS`, `TASK_RETENTION_MS`, `MAX_REQUEST_BYTES`/`MAX_REQUEST_BYTES_CEILING`), and the `BridgeDO` class. `BridgeDO`'s constructor wires each domain module and its original method names remain as thin delegates (`this.<domain>.xxx(...)`) — that surface is what the tests and `wrangler.jsonc`'s `class_name "BridgeDO"` binding depend on, so keep the names and response shapes when moving logic.

| Module | Owns |
|---|---|
| `bridge-schema.js` | `initializeBridgeSchema(sql)` — every table/migration/index, in an order that matters (notably the `needsMsgTitleBackfill` cross-table backfill runs only after both `msgs.title` and `tasks.title` exist) |
| `bridge-protocol.js` | queue/task state machine: `queueNext`/`queueSetTitle`/`queueSubmit`/`taskHistory`, `local*` task ops (`localStartTask`, `localReportTask`, `localEnqueue` idempotency, …), `localMigrateLegacyState`, read-only history rows for the dashboard |
| `bridge-admin.js` | provision/deprovision, secret rotation (`rotateSecret`/`rotateHubToken`), settings/guidance/limits/browser settings, hub registry, `maxBodyBytes`/`maxRequestBytes` and the body-size constants |
| `bridge-oauth.js` | DO-owned OAuth codes/tokens/clients, internal OAuth handlers, `checkResourceOwnerToken`, `revokeAllOAuthTokens`/`clearOAuthState` |
| `bridge-mcp.js` | dedicated/shared MCP dispatch (`handleOAuthMcpDispatch`), `invokeTool`, `list_workspaces`, the binding-only `/hub` relay (`handleHubRelay`, `handleHubToolCall`), `toolOk`/`toolError` |
| `bridge-transport.js` | `/local` dispatch (`handleLocalRoute`), `/link` WebSocket lifecycle (`handleLink`, `webSocket*`), `callLocal`/pending RPC, `rateLimit` |
| `bridge-dashboard.js` | dashboard sessions, workspace + hub dashboard handlers, `dashboardApiDispatch`, `/hub-dashboard-relay`; workspace and hub variants are deliberately kept as separate code paths inside it |
| `bridge-mcp-access.js` | `mcp_access_events` table access only: `record` (insert + row-cap trim), `dashboardRows` (filtered keyset query), `cleanupBefore`, `clearAll` — see "MCP access history" |
| `worker-http.js`, `worker-oauth-http.js`, `worker-dashboard-http.js`, `worker-mcp-access.js` | stateless helpers only (origin checks, JSON/size-limited body readers, OAuth metadata/form parsing, dashboard headers/cursors/templates; `worker-mcp-access.js`: the pure sanitizer/classifier that builds an MCP access event) — no SQL, no `env` |

Rules for changing this layout:
- **One-way dependencies: `index.js` → `bridge-*.js` → `worker-*.js`.** A `bridge-*`/`worker-*` module never imports `index.js`, and `bridge-*` modules never import each other. Cross-domain needs (e.g. admin → OAuth token revocation, protocol → transport `plan_pushed` notification, dashboard → rate limiting) are injected as narrow callbacks in `BridgeDO`'s constructor — not a catch-all context object, and not a sibling import.
- Each domain is a factory (`createBridgeProtocol({...})` etc.) taking only the `sql`/scalars/callbacks it needs. `env`/`BRIDGE_DO` access (cross-DO calls) stays in `index.js`, so the binding-only `/hub` and `/hub-dashboard-relay` routes remain visibly a `BRIDGE_DO` concern.
- Modules are plain `.js` files at the `worker/src/` root, which `scripts/check.mjs` syntax-checks automatically. `worker/src/dashboard/` holds only browser-side assets imported as Wrangler Text modules — never put an executable Worker module there.
- Byte-copying code between files with shell tools has already once written a raw control byte into a regex; after such a move, scan the touched files for control characters.

### Worker routing (`worker/src/index.js`)

Path shapes at the top-level `fetch`:
- `/admin/<ADMIN_TOKEN>` — provisioning (new workspace, hub token, rotation); machine-wide, never appears in a per-workspace URL.
- `/mcp`, `/mcp/<workspace_id>` — OAuth-protected shared and per-workspace ChatGPT MCP resources. The shared resource forwards per-tool calls to the right per-workspace DO via an internal `/hub` route. `/hub` is binding-only (fetched only from `handleHubToolCall` in `bridge-mcp.js`, never routed from the top-level `fetch`), so a DO handling a `/hub` request can assume the shared connector unconditionally — `invokeTool`'s `connector` option relies on this to pick the right operating-instructions variant.
- `/link/<workspace_id>/<link_token>`, `/local/<workspace_id>/<cli_token>` — token-protected local bridge and CLI endpoints; they are not MCP connector routes.
- `/dashboard/<workspace_id>[/...]` — the workspace-owner Web dashboard (see below). Variable-length (root shell, fixed Text-module `app.js`/`app.css`, `login`/`logout`, `api/*`), unlike every other route above.
- `/dashboard/hub[/...]` — the shared hub Web dashboard (see "Shared hub dashboard" below), routed to the hub DO instead of a workspace DO. `"hub"` can never collide with a real `workspace_id` (`isValidWorkspaceId` requires 16 hex chars or the legacy `"default"`), so this check runs before, and never shadows, the per-workspace one above it.

`workspace_id` is a routing key, not a secret (selects which DO instance); the actual `gpt_token`/`link_token`/`cli_token` are generated by `/admin` and validated **inside** the DO against its own `secrets` table — the top-level Worker never sees them.

### Web dashboard (`worker/src/bridge-dashboard.js`, reached via `BridgeDO.handleDashboard` and friends)

A browser UI for one workspace at a time, served entirely by that workspace's own DO — see `docs/plans/queue-dashboard.md` for the full design record (rejected alternatives, unresolved-at-the-time questions, and the ChatGPT review round that shaped it). It is another concrete instance of this file's "DO is the single source of truth" and "token validation stays inside the DO" invariants, not an exception to them: the top-level `fetch` only shape-validates `workspace_id` and forwards (`isValidWorkspaceId` + `idFromName`, same as `/link`/`/local`); every session/login/CSRF check happens inside `handleDashboard`.

- **Auth**: login (`handleDashboardLogin`) accepts only this workspace's own `gpt_token` via `checkResourceOwnerToken()` — never `hub_gpt_token`, because a workspace DO never has that secret set (see `checkResourceOwnerToken`'s own doc comment: hub and workspace DOs are disjoint instances). The owner token itself is never reused after login; a fresh table, `dashboard_sessions` (`session_hash` only — never the raw token, same pattern as the OAuth token tables), backs a 24h session. `createDashboardSession`/`verifyDashboardSession`/`revokeDashboardSession`/`revokeAllDashboardSessions` are the only things that touch it. `rotateSecret("gpt_token")` calls `revokeAllDashboardSessions()` (alongside the existing `revokeAllOAuthTokens()`); `deprovision()` deletes the whole table directly (it wipes every workspace table the same way, not through the individual revoke helpers); `alarm()` sweeps expired rows on its normal 24h cycle, same as OAuth codes/tokens.
- **Cookie**: `HttpOnly; Secure; SameSite=Strict; Path=/dashboard/<workspace_id>` (`dashboardSessionCookie()`). The `Path` scoping is defense in depth for a browser with multiple workspace dashboards open — the actual isolation boundary is that a session hash only ever exists in the one DO's own `dashboard_sessions` table it was created in, so a cookie sent to the wrong workspace's path always fails `verifyDashboardSession` regardless of `Path`.
- **CSRF**: every mutating (`POST`) dashboard route requires a strict same-origin `Origin` header via `checkDashboardOrigin()` — deliberately **not** the existing `checkOrigin()`, which treats a missing `Origin` as "allow" (correct for the server-to-server callers it guards, wrong here: the dashboard's session cookie is real ambient browser authority). `SameSite=Strict` alone is not treated as sufficient.
- **CSP and fixed browser assets**: `worker/src/dashboard/dashboard.css`, `common-app.js`, `workspace-panel.js`, `workspace-app.js`, and `hub-app.js` are Wrangler Text modules. `handleDashboardAppCss`/`handleHubDashboardAppCss` serve the shared CSS at same-origin `.../app.css`; the HTML links it rather than inlining it, so `dashboardHtmlHeaders()` can require both `script-src 'self'` and `style-src 'self'`. Do not add inline style attributes or `<style>` blocks to dashboard templates without revisiting that CSP. The entry JS remains same-origin at `.../app.js`, never inline; it loads the shared ESM helpers from the same dashboard base with `type="module"`.
- **Rate limiting has no bucket shared between an unauthenticated caller and an authenticated one, anywhere on this path** — `workspace_id` is not a secret, so a `/dashboard/<workspace_id>` route needs no credential to reach at all, and an earlier version of this feature gated every dashboard request (public shell, login, and the authenticated API alike) through one shared `rateLimit("dashboard", ...)` bucket before dispatch, which let an uncredentialed flood 429 an already-logged-in owner's own polling/mutations. The fix: `dashboard-public` (shell/`app.js`/`app.css`/logout), `dashboard-login` (POST login, tight — the credential-guessing surface), and, inside `handleDashboardApi`, whichever of `dashboard-api-unauth`/`dashboard-api` applies is chosen strictly by that same call's own `verifyDashboardSession()` outcome — never checked unconditionally up front. A request with a currently-valid session therefore only ever competes against `dashboard-api`, never against traffic hitting any of the other buckets. Preserve this when touching dashboard rate limiting: never reintroduce one bucket gating both an unauthenticated and an authenticated code path.
- **Mutation wrappers preserve existing protocol invariants, never bypass them**: `dashboardAck`/`dashboardDiscard`/`dashboardDiscardTask`/`dashboardStartTask` all call the same `local*` methods the CLI uses — never a second parallel implementation. `dashboardDiscard` specifically refuses a single-message discard of an active (non-`DONE`/`BLOCKED`) task's `to_gpt` row (`USE_DISCARD_TASK`), because `localDiscard` alone would leave `tasks.protocol_state` stuck with no queued INIT and no way for `localEnqueue`'s idempotency check to recover it — see `docs/plans/queue-dashboard.md`'s UI-constraint note for the full mechanism. `dashboardStartTask` is the one place a dashboard task is created, always through `localStartTask()` with a server-generated `task_id` and the CLI's own `"GOAL:\n<goal>"` body contract.
- **`localStartTask()` enqueue-failure consistency**: fixed as part of this feature. It now preflights the body-size check *and* a `task_id` collision check (`getTask(taskId)` — `task_id` is `tasks`' primary key, so an existing row, including the current active task under `force:true`, would otherwise either throw a raw SQL constraint error out of the `INSERT` or (`force`) BLOCK/discard the previous task before that throw) *before* any state mutation, and rolls back the freshly-inserted `tasks` row if `localEnqueue()` still fails for any other reason — previously an oversized `goal` could leave an orphaned `WAITING_PLAN` task with zero queued INIT, and with `force` could also lose the previous task. This applies to the CLI's `start_task` path too, not just the dashboard.
- **History APIs are retention-bounded, keyset-paginated, and separate from the debug/live-queue getters**: `dashboardMessages`/`dashboardTasks` are new, acked-including, full-history views — distinct from `localList()` (unacked-only, debug tool) and `taskHistory()` (terminal-only, and its `created_at` field is actually `updated_at` — a naming bug `dashboardTasks` does not repeat, using `updatedAt` correctly instead). Pagination is an opaque cursor encoding `(timestamp, tie-breaker id)` (`encodeDashboardCursor`/`decodeDashboardCursor`) — `(created_at, message_id)` for messages, `(updated_at, task_id)` for tasks — because the timestamp alone can't disambiguate same-millisecond rows. Backed by new indices (`idx_msgs_history`, `idx_msgs_task_history`, `idx_tasks_history`) distinct from the existing live-queue/active-task indices (`idx_q`, `idx_tasks_active`), which are shaped for different query patterns. "Retention-bounded" means exactly what `alarm()` already enforces elsewhere in this file — acked `msgs` past `RETENTION_MS` and terminal `tasks` past `TASK_RETENTION_MS` are simply gone, not merely hidden.
- **Browser nudge is a push, and is best-effort by design**: task creation via the dashboard is authoritative regardless of what happens next. `dashboardStartTask` calls `callLocal("dashboard_task_created", {taskId})` — a new sibling to the existing `plan_pushed` push — after the task already exists; the local daemon ACKs that RPC *before* running browser automation (`bridge/link.mjs`). `nudge.status` in `dashboardStartTask`'s response only reflects whether that RPC reached and was ACKed by the daemon (`"dispatched"`, `"local_offline"`, `"timeout"`, ...) — it says nothing about whether the Chrome automation itself (open tab, prepare composer, click send) actually succeeded, which happens *after* the ACK and is only ever observable in the local bridge log (`appendLog`), same as `plan_pushed`'s existing fire-and-forget behavior.
- **`dashboardOverview`/`dashboardMessages`/`dashboardTasks`/`dashboardSetGuidance`/`dashboardSetLimits`/`dashboardAck`/`dashboardDiscard`/`dashboardDiscardTask`/`dashboardStartTask` are dispatched through one shared method, `dashboardApiDispatch(name, method, request, url)`, extracted from `handleDashboardApi`'s former inline `if` chain.** It performs no auth itself — it must only ever be reached through an already-gated caller. There are exactly two: `handleDashboardApi` (public per-workspace route, gated by that method's own session/CSRF/rate-limit checks) and `handleHubDashboardRelay` (see below, gated instead by the *hub* DO's own checks before the call ever reaches this workspace's DO). Route a new dashboard operation through this dispatcher, not by adding a third place that calls the underlying `dashboard*`/`local*` method directly — that is what keeps hub-driven and owner-driven dashboard actions from ever disagreeing about validation/state semantics.

### Shared hub dashboard (`worker/src/bridge-dashboard.js`, reached via `BridgeDO.handleHubDashboard` and friends)

An owner-control-plane extension of the per-workspace dashboard above, added after the per-workspace dashboard shipped: logging in to `/dashboard/hub` with the shared `hub_gpt_token` (never a workspace's own `gpt_token` — same disjoint-secret guarantee `checkResourceOwnerToken`'s doc comment relies on) gives one browser session that can view and operate on every workspace in the hub DO's own `registeredWorkspaces()` (the `workspace_registry` table), not just one.

- **Reframing "Workspace isolation between DOs" for this feature, explicitly**: this is not an exception to that invariant, it is the owner's own control plane across workspaces *they already registered here themselves* — never a new way for one workspace to reach another, and never a way for anyone without the hub token to reach any workspace. Concretely: a hub session cannot authenticate a workspace's own `/dashboard/<id>/api/*` (different DO, different `dashboard_sessions` table, different cookie `Path`); a workspace session cannot authenticate the hub's `/dashboard/hub/api/*`; and the hub can only ever reach a `workspace_id` present in its own `registeredWorkspaces()` — never an arbitrary valid-looking 16-hex id, even though `isValidWorkspaceId` alone would accept it. Preserve this membership check (`hubDashboardRelay`, mirroring the existing `handleHubToolCall`'s identical check for the MCP tool relay) if you touch hub dashboard routing.
- **Authorization propagation, hub DO → workspace DO: a binding-only internal relay, not a forwarded token.** `hubDashboardRelay`/`hubDashboardWorkspaces` (hub DO) call a new internal-only route, `POST /hub-dashboard-relay` (`handleHubDashboardRelay`, workspace DO) — reachable only via a `BRIDGE_DO` binding call, never routed from a public URL (no path shape in the top-level `fetch` maps to it), exactly the same shape as the pre-existing `/hub` route (`handleHubRelay`) used for the MCP tool relay. The hub DO has already verified its own dashboard session, CSRF origin, rate limit, and registry membership *before* this is ever called; the workspace DO does not (and structurally cannot) re-derive who the hub-side browser caller was — the binding call itself is the authority, same as `/hub`. **The hub's session cookie and `hub_gpt_token` are never forwarded to the workspace DO** — only the already-authorized operation name/method/query/body. This is what keeps "token validation stays inside the DO" true for this feature too: `hub_gpt_token` is validated only inside the hub DO, never copied to or re-checked by a workspace DO. Do not "simplify" this by forwarding the hub token to the workspace DO and letting it validate there — `checkResourceOwnerToken()`'s `hub_gpt_token || gpt_token` OR-check exists for OAuth's single-DO-is-either-role case, not as a cross-DO trust mechanism, and reusing it that way would let a hub token authenticate a request that looks like it came from the workspace's own owner.
- **A registry entry can outlive a workspace's own `deprovision()`** — `unregister_workspace` and `deprovision` are two separate `/admin` calls (see `bridge/cli-provision.mjs`'s `cmdRemove`, which issues both), so a stale registered-but-deprovisioned target is expected, not a bug to "fix" by making them atomic. `handleHubDashboardRelay` guards this with its own `hasSecrets()` check (`NOT_PROVISIONED`) rather than silently recreating task/settings state for a workspace that no longer has tokens; `hubDashboardWorkspaces` surfaces that per-entry as `{overview: null, error: "NOT_PROVISIONED"}` rather than failing the whole listing.
- **Session/cookie**: reuses the exact same `dashboard_sessions` table, `createDashboardSession`/`verifyDashboardSession`/`revokeDashboardSession`/`revokeAllDashboardSessions` methods, and `dashboardSessionCookie()` helper as the per-workspace dashboard — just called on the hub DO's own instance of that table, and with the literal string `"hub"` in place of a `workspace_id`, which naturally produces `Path=/dashboard/hub`. No new session mechanism was introduced. `rotateHubToken()` now also calls `revokeAllDashboardSessions()` (mirroring `rotateSecret("gpt_token")`'s existing call for the per-workspace case), so rotating the shared hub token immediately cuts off hub dashboard sessions issued under the old value; it does not touch any workspace DO's own sessions, and rotating a workspace's `gpt_token` does not touch the hub's.
- **Rate limiting uses its own bucket names, never shared with a workspace's own dashboard buckets**: `hub-dashboard-public`, `hub-dashboard-login`, `hub-dashboard-api-unauth`, `hub-dashboard-api` (hub DO, same two-tier unauthenticated/authenticated split as the per-workspace `dashboard-*` buckets, and the same reasoning: an unauthenticated flood must never 429 an already-authenticated caller), plus `hub-dashboard-internal` (workspace DO, consumed only by `handleHubDashboardRelay` — so a burst of hub-driven management traffic into one workspace can never rate-limit that workspace's own owner dashboard, or vice versa).
- **Envelope size gate uses the same fixed-ceiling pattern as `handleOAuthMcpDispatch`'s hub-level branch, for the identical reason**: `hubDashboardRelay` doesn't know the target workspace's own `max_body_bytes` setting before relaying (that's per-workspace DO state), so its own pre-relay size check uses `MAX_REQUEST_BYTES_CEILING` rather than a precise value; the real, precise limit is enforced once the call reaches the target's own `dashboardApiDispatch` via `this.maxRequestBytes()`. Do not "fix" this asymmetry by widening it — see that existing comment for why it's deliberate.
- **UI**: `renderHubDashboardLoginHtml`/`renderHubDashboardShellHtml`/`HUB_DASHBOARD_APP_JS` are a structurally-parallel but separate set from the per-workspace `renderDashboardLoginHtml`/`renderDashboardShellHtml`/`WORKSPACE_DASHBOARD_APP_JS` (same look, CSP, and textContent-only rendering discipline — see the latter's own doc comment for why untrusted content is never inlined as HTML), extended with a workspace list/selector step. Both entries share `COMMON_DASHBOARD_APP_JS` and the workspace-panel asset over their own same-origin bases. Every per-workspace action in the hub UI targets `/dashboard/hub/api/workspaces/<id>/...` instead of `/dashboard/<id>/api/...`.

### MCP access history (`mcp_access_events`, the dashboards' "MCP Access" tab)

An audit trail of what ChatGPT did through MCP, shown next to Tasks/Messages in **both** the per-workspace and hub dashboards. Design record: `docs/plans/pending/mcp-access-history-dashboard.md` (gitignored).

- **One recording point.** Every tool call — dedicated (`handleToolCall`) and shared (hub → binding-only `/hub` → `handleHubRelay`) — passes through `bridge-mcp.js`'s `invokeTool`, which wraps `dispatchTool`. It snapshots `startedAt` and the active `task_id` *before* dispatch, then builds the event from the finished result and calls the injected `recordMcpAccess` (`BridgeDO.recordMcpAccess` in `index.js`). Recording sits in a try/catch: **a recording failure must never change or fail an MCP response.** Do not add a second recording site (e.g. in `handleHubRelay`) — the shared path would then be counted twice.
- **Privacy is enforced in one pure module, `worker-mcp-access.js` (`buildMcpAccessEvent`), not by callers.** Stored: time, duration, tool, connector, task id, a *safe target*, result class + short code, and for `workspace_batch` at most `MAX_BATCH_DETAIL_CALLS` (8) per-call summaries capped at `MAX_DETAILS_BYTES` (4096). **Never stored:** file contents, diffs, search queries/globs/hits, message bodies or titles, result/error message text, raw args/results, secrets, absolute or outside-workspace paths. Targets come from a fixed vocabulary (`summarizeTarget`) plus `safeWorkspacePath`-sanitized paths (rejects absolute/UNC/drive/URL/`..`/control characters, caps 240 code points); anything else is a fixed label. Every stored string comes from a **closed set**, not merely an identifier-shaped one: tool names (`MCP_TOOL_NAMES`, else `unknown`), a batch sub-call's tool (taken from the *input* call and limited to `MCP_BATCH_TOOL_NAMES`, mirroring `bridge/link.mjs`'s `BATCH_WHITELIST` — never from the result), and outcome codes (`MCP_OUTCOME_CODES`, else `UNKNOWN`; an unlisted `ACCESS_DENIED_*` collapses to `ACCESS_DENIED`). A new error code that should be shown by name must be added to `MCP_OUTCOME_CODES` (and `MCP_CODE_TEXT` in `common-app.js`); the size cap `MAX_DETAILS_BYTES` is measured in UTF-8 bytes. Result text is never copied — `classifyResult` maps to `success` / `gate_denied` (`no_active_task`, `task_window_expired`) / `access_denied` (`ACCESS_DENIED_*`, `OUT_OF_WORKSPACE`) / `error` / `mixed` plus a code. When adding a tool or a field, extend `summarizeTarget` deliberately; the default for an unknown tool is *no target*, not "stringify the args". `tests/mcp-access.test.mjs` pins these privacy rules.
- **Retention:** 24 hours (`MCP_ACCESS_RETENTION_MS`, swept by `alarm()` via `cleanupBefore`) **and** 1000 rows (`MCP_ACCESS_MAX_ROWS`, trimmed on every insert by a primary-key range delete). The tab is a *live view of activity*, not a long-term audit log — that is why both numbers are small (they were 7 days / 5000 first). The cap matters because this table grows with every tool call, unlike `msgs`/`tasks`, and because it bounds the worst-case scan of a rare `tool`/`outcome` filter: only `(started_at, event_id)` is indexed, so a filter that matches few rows walks every row (verified with `EXPLAIN QUERY PLAN`), i.e. at most this cap. `alarm()` runs once a day, so a row can outlive the retention by up to a day; `dashboardMcpAccess` therefore passes `since = now - retention` and `dashboardRows` hides such rows instead of relying on the sweep. `deprovision()` clears it (`clearMcpAccessState`). It is audit metadata, not task state — the DO-is-authority invariant is unaffected, and nothing reads it back into protocol decisions.
- **Dashboard API:** `GET .../mcp-access?limit&cursor&tool&outcome` through `dashboardApiDispatch` (so the hub relay reaches it as `/dashboard/hub/api/workspaces/<id>/mcp-access` with no whitelist to update). `tool`/`outcome` filters are applied in SQL so they hold across pages. Keyset cursor reuses `encodeDashboardCursor`, which needs a string id: `event_id` is stringified and re-parsed with `^\d{1,15}$`, a non-integer cursor being treated as none. The response never contains anything beyond the stored metadata.
- **Live updates use their own scope, `"mcp"`, and it must never fall through to a Tasks/Messages reload.** `recordMcpAccess` calls `notifyDashboardInvalidation("mcp")` behind a leading-edge throttle (`MCP_NOTIFY_MIN_INTERVAL_MS`, 2 s) because ChatGPT can make many calls per second and the workspace DO also notifies the hub DO each time. Because the dashboard stops polling while its WebSocket is healthy, a throttled (skipped) notification is recovered in the browser: `workspace-panel.js`'s `handleMcpInvalidate` reloads immediately **and** schedules one trailing "settling" reload after `MCP_SETTLE_MS` (2.5 s, must stay longer than `MCP_NOTIFY_MIN_INTERVAL_MS`); a newer notification replaces the timer, and leaving the MCP tab or switching workspace cancels it. Do not "fix" a missing tail by shortening the Worker throttle or adding a DO-side timer. In the browser, `workspace-app.js` (`handleInvalidate`/`mergeScope`) and `hub-app.js` (`handleWorkspaceInvalidate`/`mergeWorkspaceScope`) route `"mcp"` to `panel.handleMcpInvalidate()`, which reloads only if the MCP tab is showing; for an unselected hub workspace it does nothing (no status read). A queued (hidden-tab) `"mcp"` stays `"mcp"` unless something stronger arrives. `workspace-panel.js`'s `pollActivity` has an MCP branch (history + overview strip, no snapshot) for the polling fallback.
- **UI rules** (`common-app.js` helpers + `workspace-panel.js`): untrusted text (target, code, tool name) is only rendered via `el()`/`textContent`; the outcome badge is a text label with a class (never colour alone); `groupMcpEvents` folds only consecutive *successful* `read_file` of the same task **and the same connector** (a group's detail shows one connector, so mixing them would misreport it) within `MCP_GROUP_GAP_MS` (30 s) — denials/blocks/errors are never folded — and a group's id is its oldest member's so a selected group stays selected as it grows; filters reset when the workspace changes; a monotonic request generation (`mcpRequestGen`) drops responses that arrive out of order. Tests: `tests/mcp-panel.test.mjs` runs the real panel code against `tests/helpers/fake-dom.mjs` (which throws on `innerHTML`/`outerHTML`/`insertAdjacentHTML`); `tests/mcp-dashboard-assets.test.mjs` pins shells, scope routing and CSS. Run them with `node --test --import ./tests/helpers/text-modules.mjs <file>` (the dashboard assets are Wrangler Text modules).

### CLI (`bridge/cli*.mjs`)

`bridge/cli.mjs` is the compatibility facade, sole executable entry point, and explicit dispatcher. Command implementation ownership is:

| Module | Responsibility |
| --- | --- |
| `cli-runtime.mjs` | shared argument, workspace, local/admin RPC, and legacy-migration seam |
| `cli-browser.mjs` | browser settings and chat commands |
| `cli-provision.mjs` | init, remove, URL, workspace listing, config display, and rotation |
| `cli-daemon.mjs` | start/stop/status and dashboard nudge callback |
| `cli-task.mjs` | queue, task, wait, report/handoff, completion, and state |
| `cli-settings.mjs` | guidance, limits, and allow-read commands |

All command modules may depend on `cli-runtime.mjs`; `cli-provision.mjs`, `cli-daemon.mjs`, and `cli-task.mjs` may also depend on the lower-level browser service in `cli-browser.mjs`. `cli-browser.mjs` must not import them back, and no command module may import `cli.mjs`.


`gpt-worker handoff` and `gpt-worker report` (`cmdHandoff`/`cmdReport`) are the same round — both delegate to `reportRound(args, handoff)`; the only difference is the `HANDOFF:` section `buildExecutedBody()` appends and the closing message. `handoff` deliberately covers *both* directions of a hand-off — the agent that did this round's work stopping, or a fresh agent proactively taking over a round the previous agent left without reporting — with a single command and a plain-language `reason`, not a mode/trigger flag: `report_task` doesn't know or care which local agent is calling it, only `task_id`/`iteration`/protocol state, so nothing server-side distinguishes the two callers anyway. When claiming an abandoned round, pass an honest `reason` and skip `--changed`/`--tests` (or say plainly nothing is verified) rather than inventing a report — the `"?"`/`"(not run)"` defaults already exist for exactly this, and `EXECUTED` review (`worker/src/instructions.md` §7) already requires GPT to re-verify via `git_status`/`git_diff` regardless of who's asking, so no extra field is needed to make GPT skeptical. `report_task`'s ordinary `EXECUTING`-only precondition is what makes a claiming `handoff` valid in exactly the situation it's for (a round left mid-execution) and invalid otherwise (`INVALID_STATE` when a reply is already queued — `wait` picks that up, not another `handoff`). Do not reintroduce a `claim` subcommand or a `trigger` field for this — it was tried and reverted; the free-text `reason` plus the existing state precondition already cover it, and CHANGED_FILES/TESTS' own long-standing `"?"`/empty defaults already say "unspecified." Agent-to-agent handoff needs no per-agent state precisely *because* of the invariants below: `localPoll` selects `to_local` rows without looking at who asked, `selectWaitMessages` filters by `task_id` alone, and `cmdWait` reads the active task from the DO rather than from local state — so a second agent resumes with a plain `wait`. Do not add an agent identity or a queue-level lease/lock to "fix" this; sequential handoff does not race, and that filtering is what makes the feature work. The receiving side keys off a `HANDOFF_BRIEF:` marker at the start of a PLAN body (written by ChatGPT per `worker/src/instructions.md` §8), so treat that marker as protocol, not cosmetics.

`gpt-worker limits` reads/writes a workspace's own `settings.max_body_bytes` (`maxBodyBytes()`/`localMaxBodyBytesGet()`/`localMaxBodyBytesSet()`, implemented in `worker/src/bridge-admin.js` and exposed as `BridgeDO` delegates), overriding the `MAX_BODY_BYTES` (16 KiB) default up to `MAX_BODY_BYTES_CEILING` (256 KiB). It is per-workspace DO state, not a Worker-wide constant — no redeploy needed to change it, consistent with the DO-is-the-authority invariant elsewhere in this file. `maxRequestBytes()` (`maxBodyBytes() + REQUEST_ENVELOPE_OVERHEAD_BYTES`) must stay in sync wherever `body` is size-checked: `queueSubmit`/`localEnqueue` check the body itself, `handleLocalRoute`/`handleHubRelay`/the dedicated-connector branch of `handleOAuthMcpDispatch` check the request envelope around it. The shared connector's hub-level envelope gate (`handleOAuthMcpDispatch`'s `useHubHandler` branch) is the one exception — it runs on the hub DO before `arguments.workspace_id` has been parsed out, so it can't yet know which workspace's limit applies and is fixed at `MAX_REQUEST_BYTES_CEILING` instead; the real per-workspace limit is enforced once `handleHubToolCall` forwards the call to that workspace's own DO (`handleHubRelay`). Do not widen this gate's fixed ceiling to "fix" that asymmetry — it is deliberate, not a gap.

Each `gpt-worker <cmd>` subcommand talks to the Worker over `/local/<workspace_id>/<cli_token>` (`localCall`) for queue/task operations. `cmdWait` (the most failure-prone command to modify) already polls the Worker in ~20s chunks for its whole `--timeout` window (default 900s) — it is a single blocking call by design; if you change its retry/backoff behavior, keep that property, since [SKILL.md](SKILL.md) explicitly instructs agents to call it once and let it block rather than wrapping it in their own sleep/retry loop.

**Worker transport (`bridge/cli-runtime.mjs`'s `localCall`/`adminCall`)** used to be a bare `fetch`; it now has a per-call timeout (15s; `poll` gets its own `timeout_ms` + 10s because it is a long-poll) and retries, but *which* failures are retried is the whole design and must not be loosened casually. A read op (`IDEMPOTENT_OPS`, plus any `*_get`) is retried on any transport failure. A **mutating** op is retried only when the request provably never arrived — a refused/unresolvable connection (`NEVER_SENT_CODES`) — or on HTTP 429 *from `/local`*, which `handleLocalRoute` answers before it parses or dispatches, so the op did not run. That reasoning holds only for `/local`: `/admin` has no such gate (it forwards to a Durable Object), so a 429 there proves nothing about whether a rotate/deprovision/register ran and `adminCall` retries it only for read ops — `throttleBeforeDispatch` is set by `localCall` alone. A timeout, a dropped connection or a 5xx on a mutating op is **not** retried, because "never arrived" and "arrived but the reply was lost" cannot be told apart, and repeating e.g. `report_task` fails with `INVALID_STATE` at best; it throws `WorkerUnreachableError` with `maybeApplied: true` and a message telling the user to check `gpt-worker state`. Structured errors in a normal response and 4xx are returned as before, never retried. `localCall` therefore *throws* on exhausted transport failure where it used to return `{error:"HTTP_<status>"}`; callers that already tolerated a throw (`loadChatSettings`, `cmdStatus`, the daemon's nudge callback) are unchanged. `cli.mjs`'s `main().catch` prints `WorkerUnreachableError`/`WorkerCallError` as a plain message (exit 4 / 1) and keeps the stack for anything unexpected. Exit codes: 0 ok, 1 error, 2 `wait` timed out, 3 a reply was delivered but the task did not advance, 4 Worker unreachable. `GPT_WORKER_RETRY_BASE_MS` (default 300) and `GPT_WORKER_WAIT_RETRY_MS` (default 5000) exist only so tests can exercise these paths in milliseconds; nothing in production sets them.

**CLI diagnostics and preflight**: `remoteActiveState()` preserves the Worker-owned `{task, taskWindow}` response while `remoteActiveTask()` remains the task-only compatibility wrapper; `cmdStatus` must use the former so it never copies the read-window idle constant. It prints all local diagnostics first and must distinguish remote unreachability from an empty task. Its `status`/`active_task`/body-limit reads share a 25s diagnostic deadline; when that cannot verify remote browser settings, print chat as unavailable rather than falling back to a misleading `unbound`. `gpt-worker logs` reads only local state and supports the current log plus one rotation; it deliberately has no follow mode. `logs --all` must address each saved `stateDir` directly, because `tokens.json.workspacePath` can point to a moved or deleted directory. `bridge/cli-help.mjs` is pure command metadata and formatting: update its `COMMANDS`, the dispatcher, and the English README command table together (the test enforces the latter two). `cmdInit` calls `checkPrerequisites()` before Cloudflare work unless `--skip-preflight` is explicit; Node's required version comes from `package.json`, Git and the secret scanner are fatal, and `rg`/Chrome are informative. On a first deployment, Wrangler's parsed `*.workers.dev` URL is the authority for `ADMIN_TOKEN`: an optional `--worker-url` is only an exact-match assertion, never an unverified destination. Daemons have `stdio:"ignore"`, so scanner refusal, spawn/SIGTERM, and fatal process handlers must leave a body-free `bridge.log` record. `writePidFile` records `alwaysAllow` for the status read-gate display; preserve compatibility with old pid files that lack it.

**`cmdWait` stays one blocking call** but is no longer killed by a network blip: when the Worker is unreachable it keeps polling until its own deadline and, if it *ends* on a failure, exits 4 rather than the "no message yet" exit 2. A structured error from `poll` (e.g. a rotated token) throws `WorkerCallError` instead of being read as "nothing yet" — the old loop re-polled at full speed until the deadline. Each message is **printed before it is acked**: an ack that reaches the Worker but whose reply is lost (with every retry failing too) still marks the message delivered, so acking first could remove a body from the queue without the agent ever having seen it. Printing first means the agent always has the body. What an *unconfirmed* ack leaves behind cannot be known from the CLI, and there are three outcomes needing three different next steps: (1) the ack landed and the task advanced — the reply is **not** redelivered, so act on the printed one; (2) it never landed — the task still waits for it and the reply is still queued, so `wait` delivers it again (acting first makes `report_task` fail with `INVALID_STATE`); (3) the reply was recorded as delivered but the task did not advance — `localAck` marks the message acked *before* it validates the transition, so a mismatch plus lost responses does this — leaving the task waiting for an ack whose message is gone, which nothing will ever redeliver. The task's state separates (1) from the rest, but only the queue separates (2) from (3), so the command exits 4 and sends the agent to both `gpt-worker state` and `gpt-worker queue` rather than promising a redelivery; (3) is a stuck task and ends in `discard-task`. After each ack it consults `findStuckAck()`: the Worker's `localAck` reports `acked`/`already_acked`/`transitioned`/`reason`/`task`, and an acked message that left a still-open task waiting means the reply will never be redelivered (the to_local queue is now empty). Then a warning and exit 3. A task already terminal, and an older Worker without these fields, are deliberately *not* flagged. `already_acked` is exempt only when the task has moved off `LOCAL_*_ACK`: an applied transition never leaves a task still waiting for a local ack (PLAN → `EXECUTING`, BLOCKED → `USER`, DONE → `DONE`, iteration-0 DONE → `LOCAL_DECISION`), so a task that still is was never advanced — this catches a first ack that marked the message delivered but failed to transition, whose retry reports `already_acked` too. **`wait` also surfaces the `workspace_bundle` approval hint, without ending early.** `BridgeDO.bundleHint()` (`worker/src/index.js`) returns `{code, at, ageMs}` when the task is `WAITING_PLAN`/`WAITING_REVIEW` and the newest `mcp_access_events` row is a *successful `workspace_bundle` of this task that started after the task last moved* (`tasks.updated_at`); `localPoll` attaches it to an **empty** poll as `hint` and the `active_task` op carries it as `bundleHint` for `status`. It is decided in the Worker, not the daemon, because `next_task`/`submit_plan` are answered by the Durable Object and never reach the bridge, so only the DO sees the whole sequence; it joins two domains, so like `active_task` it lives in the composition root. The CLI decides only *when to speak* (`bundleHintMessages()` in `bridge/cli-runtime.mjs`, shared because command modules may only depend on `cli-runtime.mjs`): a notice when a hint is first seen, one reminder after 2 minutes of silence, then every 5 minutes (initial values), all on stderr and in `bridge.log`. At the deadline the exit code is still 2 and `--timeout` is still a real deadline — only the stdout sentence changes (still starting `No message yet.`), and it is repeated on stderr; with no hint the output is byte-for-byte what it was. **It is a hint, never a finding:** a pending ChatGPT approval dialog and ChatGPT reading the archive afterwards are both silence after a bundle, so every message says "may", and a bundle that succeeded with zero files (no attachment, so no dialog) is a known false positive. It carries no content — no path, size or file name. `tests/queue.test.mjs` ("poll hint") pins when it appears; `tests/bundle-hint.test.mjs` and `tests/cli-task.test.mjs` ("wait: workspace_bundle hint") pin what is printed. `--timeout` is a real deadline: it is passed to every call `wait` makes as `deadlineMs`, which clamps each attempt (plus a 2s grace so a long-poll held to exactly the deadline is not aborted at its own finish line) and stops retries starting after it — checked both before and after the retry pause, because the pause is clamped to the time left and can end exactly at the deadline. This covers the calls `wait` itself makes (the task lookup and the polls); the one-time legacy-state migration that runs first (only when legacy files exist) is outside the deadline and keeps its own retry budget, since cutting a half-finished migration short would be worse than a rare overrun.

`gpt-worker discard-task [--task <id>] --yes` (`cmdDiscardTask`) is the CLI's way out of a stuck task; before it, the only routes were `task --force` (which starts a *new* task as a side effect) or the Web dashboard. It always targets the active task — at most one task is ever non-terminal, so `--task` can only confirm the target, never reach another one — and requires `--yes` because it is destructive and agents run non-interactively (no y/n prompt possible). It goes through the same `discard_task` op the dashboard uses.

**Lock files (`bridge/state.mjs`)**: `worker.json.lock` and `tokens.json.lock` record their holder (`{pid, startedAt, createdAt}`). A lock whose holder is gone, or whose pid was reused by another process (start-time fingerprint, same idea as the bridge pid file), is broken instead of waited on; a lock with no recorded holder — or whose live holder recorded no start time, so a live pid cannot be told from a reused one — is judged by age (30s — critical sections are milliseconds); so is a lock whose recorded start time cannot be compared because `ps` fails now. `fixPermissions()`, which already runs at the start of every CLI invocation, also removes stale locks, so a killed process no longer wedges every later config/token update until someone `rm`s a file by hand. `releaseFileLock` only unlinks the lock if it is still the one *this* process created (inode check). The residual race is stated in `removeStaleLock`'s comment: two processes can break the same stale lock at once; the worst case is a lost update of a small JSON file (writes are temp-file + rename, so it is never torn).

## Key invariants to preserve when editing

- **DO is the single source of truth for task/protocol state.** Never let the CLI or bridge reconstruct or cache task state independently (see the comment at the top of `bridge/state.mjs`).
- **Workspace isolation between DOs.** A change to routing or `idFromName` calls must not let one workspace's queue, tokens, or WebSocket link become reachable from another's.
- **Token validation stays inside the DO**, not at the top-level Worker `fetch`.
- **Exactly two trusted inputs, with different provenance.** (1) The Worker-owned operating protocol in `worker/src/instructions.md`, parsed by `worker/src/instructions.js` — static text compiled into the Worker, delivered in `InitializeResult.instructions`, by the `operating_instructions` tool, and in the `operating_instructions` field of a non-empty `next_task` result (or conditionally omitted when `known_instructions_version` matches the server version). It is trusted because nothing outside this repository can reach it; never interpolate workspace, CLI, or ChatGPT data into it. (2) `workspace_guidance` — the only trusted input from the **local** side, set through the owner-authenticated CLI. Everything else ChatGPT reads is untrusted workspace data (see `UNTRUSTED_NOTE` in `bridge/tools.mjs` and the protocol doc). Don't blur either line when adding new tools.
- **Local state files are private by default** (`0700` dirs / `0600` files, self-healed by `fixPermissions()` in `bridge/state.mjs`) — any new local state file must go through the same helpers, not raw `fs.writeFileSync`.
- **What goes to ChatGPT is scanned before it is packed or sent, and nothing in it can switch the scan off.** Text leaves go through `reply()`; the one exception is a `PreScanned` archive (see "workspace_bundle"). Scanner flags and working directory are part of this invariant: keep `--ignore-gitleaks-allow` and the isolated cwd.
- **A timeout is never an answer, and on an access check it fails closed.** Every synchronous child process has a budget (`bridge/exec-limits.mjs`); a result cut short by one must be reported as a timeout, never returned as if complete, and `IgnoreRules.isGitIgnored` denies on anything but git's definite answer (exit 1 = "not ignored") rather than reading a failure as "not ignored".
- **A mutating CLI call is retried only when it provably did not run** (connection never established, or HTTP 429 from `/local`). Timeouts and 5xx on a mutating op surface as `WorkerUnreachableError` with `maybeApplied` set, never a silent retry.
- **Idempotent enqueue**: `localEnqueue` reuses an existing message for a repeated `(task_id, iteration)` instead of creating a duplicate, since a CLI retry after a dropped HTTP response must not double-post. Preserve this if you touch queueing.

## Tests

`tests/` uses Node's built-in test runner (`node --test`) against a fake Durable Object context (`tests/helpers/fake-do-ctx.mjs`) or a real temporary git repo (`tests/tools-containment.test.mjs`), not Miniflare — `tests/tools-containment.test.mjs` also covers the workspace-containment and `allowedReadFile` exact-file boundary (including sensitive paths and escaping symlinks). `queue.test.mjs` and `admin.test.mjs` import the real `BridgeDO` from `worker/src/index.js` and exercise its (delegating) methods directly against `this.sql`, so DO logic changes in any `bridge-*.js` domain module are covered without deploying — test through the `BridgeDO` delegates, not by importing a domain module directly. When adding a workspace tool or a queue/admin op, add or extend a test in the matching file rather than introducing a new test harness. `tests/dashboard.test.mjs` follows `tests/oauth.test.mjs`'s pattern instead (a real `BridgeDO` instance behind the same `env.BRIDGE_DO` binding shape, routed through the actual top-level `fetch`) because dashboard routing/session/CSRF/workspace-isolation behavior lives partly in the top-level `fetch`, which a `makeFakeCtx()`-only DO instantiation doesn't exercise. `tests/link.test.mjs` covers `BridgeLink`'s RPC dispatch against a fake in-memory WebSocket, not a real connection: `dashboard_task_created`'s ack-before-callback ordering and failure isolation, `workspace_batch` containment, and the read-window gate (the two refusal statuses, older-Worker compatibility, control-key stripping, and which lines reach `bridge.log`). Its gate tests replace `link.log` with an in-memory collector rather than writing into the real per-workspace state directory. `npm run coverage` runs the same suite with Node's `--experimental-test-coverage`; it is intentionally separate from `npm run verify` so the experimental reporting flag is not a normal CI gate.

The CLI is tested as a real process against a real HTTP server, not against stubs: `tests/helpers/fake-worker.mjs` provides `startFakeWorker(handler)` (an ephemeral-port server that can answer normally, delay, hang, or drop the connection) and `runCli(args, {env})`, and a fixture points `GPT_WORKER_CONFIG_DIR`/`GPT_WORKER_STATE_ROOT` at temp directories with a `worker.json` whose `workerUrl` is that server. `runCli` is async on purpose: the fake Worker lives in the test process, so a synchronous `execFileSync` would block the event loop the server needs and deadlock. A fixture `worker.json` with **no `chatUrl`** makes `nudgeChatGpt()` return early, so nothing reaches Chrome automation or opens a browser. `tests/cli-runtime.test.mjs` covers the transport (which failures retry, which must not) and `migrateLegacyStateIfNeeded`; `tests/cli-task.test.mjs` covers `wait` (exit 0/1/2/3/4, the stuck-ack warning, survival of a mid-wait outage), `discard-task` and `report`/`handoff`; `tests/exec-timeouts.test.mjs` puts a fake `git`/`rg` first on `PATH` and shrinks the budgets to prove the access-control probe fails closed — it is its own file because it rewrites `PATH` for the whole process and `tools.mjs` caches whether `rg` exists. A helper's reply description (`{status}`, `{destroy}`, `{hang}`) must be returned from a *function* in `cli-task.test.mjs`'s `opsHandler`; a plain object there is the body of a 200, which silently turns a "500" test into a success. `tests/bundle.test.mjs` runs `workspaceBundle()` against a real temporary git repo and the real scanner (what is included/excluded, masking including `gitleaks:allow` lines, `allow-read`/`deny-read`, `path`, limits, `scanDirectory`); `tests/bundle-failclosed.test.mjs` puts fake `betterleaks`/`git` first on `PATH` (like `exec-timeouts.test.mjs`, so its own file) to prove a broken or untrustworthy scanner produces no archive and that git not answering is reported as incomplete; `tests/bundle-delivery.test.mjs` covers the `PreScanned` path through `BridgeLink.reply()` and the Worker's `toolBlob()`. Lock behavior is covered in `tests/worker-config.test.mjs`, and `openInChromeAndSubmit`'s time budget in `tests/mac-chrome.test.mjs` through its `_exec` seam.
